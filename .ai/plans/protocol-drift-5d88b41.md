### C7 detail: what depends on telling "denied" from "absent"

1. `src/dm/dm-client.ts` `sendRequest`: asks the recipient's inbox for a credential to learn whether an inbox exists (`SpaceNotFound` = no inbox, `UserNotAuthorized` = exists, sender not a member). A non-member now gets `SpaceNotFound` either way, so **the probe can no longer detect a missing inbox** and a request to a user with no inbox reads as delivered again. This was the fix for real-browser finding 4 and BDD scenario "A DM request to a user without an inbox". Needs a replacement; see decision D2.
2. `src/dm/dm-client.ts` `classifyHalfError` and `isPending`: `revoked` ("revoked your access") collapses into `missing` ("hasn't replied"), so a participant who removes you looks pending and `renotify` keeps re-sending.
3. Revocation purge: `src/workspaces/{read-model,cache,channels,channel-sync}.ts`, `src/app/api/channels/{messages/write,reactions}/route.ts` treat status 401/403 as "access lost, drop the cache". A removed member's credential mint now fails with `SpaceNotFound` (status 404 in `SpaceCredentialError`), which none of those sites treats as lost access. **This is a security-relevant regression if left unhandled**: the scenario "Keep private cached data out of use after access is revoked" depends on it.
4. `src/workspaces/accept-errors.ts`: "not a member" and "workspace missing" messages merge.
5. `src/reader/independent-dm.ts`: same `revoked` classification.
6. `src/auth/permission-sets.ts`: the DM scope `space:org.slack.dm.inbox?authority=*&action=read` exists only for the probe in item 1.
7. Tests, features and docs that assert `UserNotAuthorized` or 403 (`bdd/steps/{channels,lifecycle,dm-conversations}.steps.ts`, `bdd/support/private-requests-ui.ts`, both inbox/DM conformance tests, pin doc "Existence oracle" row).

## Outcome and departures from this plan

Implemented as written in the phases above, with these differences. Each was forced by something the run showed, not chosen up front.

1. **Dependency install (P1).** The alpha packages' `^0.0.0-spaces-alpha-<stamp>` ranges also match stray `0.0.0` releases of `@atproto/lex-cbor` and `@atproto/lex-data`, which still list `workspace:*` dependencies, so `pnpm add` failed. `pnpm-workspace.yaml` now overrides both ranges to the snapshot (with `minimumReleaseAgeExclude` entries for the fresh snapshot). The browser-bundle gate passed: 353 KB unminified, 77 KB gzipped, no `node:` imports.
2. **Refusals are reported as 403, not 404 (P5).** The plan had `SpaceNotFound` map to 404 and a predicate treat 404 as lost access. The UI keys its "grant access" boxes on 401 or 403 from the app's own API, so a 404 broke the permission flow (reproducible, deterministic). `exchangeSpaceCredential` now reports every refusal, `SpaceNotFound` included, as 403 (410 for a deleted space); the `code` still distinguishes cases for the DM half statuses. `isAccessLost` stays the single predicate and replaced six copies.
3. **DID-document key types.** PLC documents list `#atproto_kem` as the older `EcdsaSecp256r1VerificationKey2019` (bare compressed point), not `Multikey`; `kem-key.ts` reads both. The server also caches KEM keys for ten minutes (bounded, refreshed on a failed MAC); without that every credentialed read cost a PLC fetch.
4. **MAC handling (P4).** The body is read once within the size bound and replayed after verification (a cloned stream hung on an oversized body, found by the Codex review); a record's JSON value is converted back to Lexicon form before its CID is checked (a `$link` or `$bytes` field otherwise failed verification, found by the Sonnet review); `listRepoOps` was dropped from the MAC methods because nothing calls it and a commit-less page carries no MAC.
5. **Writer eviction side effects (P2).** `removeMember` and `putMember write:false` evicting a writer changed three behaviors: the DM inbox scan now also reads every active allowlist entry's repo (otherwise a request sent while a sender was switched off stays invisible after switching back), the private-request BDD scenario reaches "tracked writer the member list does not name" through a temporary `publicWrite` window instead of removing a member, and a member who leaves, is dropped by a privacy transition or archive, or is removed and added back loses their earlier messages from a cold-cache channel history until they write again (documented in the pin note as open). The extra allowlist reads would otherwise cost one request per co-member on every 60 s poll, so a member found with nothing to read is not asked again for five minutes unless the allowlist or request mode changes or they appear as a writer (the independent code review's critic found this cost).
6. **DM declaration (P6).** `enableDms` publishes it last and `setRequestMode` repairs it, both through `ensureDeclaration` so a valid record is never rewritten (a rewrite on every settings change would be a public commit), the sender's check validates the record itself (`uri`, `$type`, `createdAt`), and `setRequestMode` reads the current policy and changes only `publicWrite`.
7. **A UI race fixed on the way (P8).** A background channel-read failure used to reset the "grant request access" box and the request-submitted state, so the button could detach while being clicked (about a third of runs of two scenarios failed after this change moved the timing; baseline 0 of 6). `resetChannelContent` now keeps that state on the read-failure path only.
8. **Per-repo isolation.** A writer or DM participant whose repo cannot be authenticated (no usable KEM key, or a MAC that fails) is set aside with a degraded note (channels) or read as a missing half (DMs) instead of failing the whole read.

12. **Declined review findings and open owner decisions, with reasons.**
    - *A dedicated 4 KiB fetch for the declaration read* (code review): every credentialed read of a recipient host has the same 8 MiB cap, and a second fetch path would duplicate XRPC error handling.
    - *Reading own data over OAuth instead of a credential* (code review): a design change the migration does not require; the pin note states every account needs a published KEM key.
    - **Owner decision 2026-10-31, keep transport trust: authenticating `listRecords` bodies** (Codex, blocking in every gate round). Prompt 10-22 section 4f ends "Do not accept commits or records from space-credential reads without a verified MAC", and section 4d says "listRecords, getBlob, listBlobs, and listRepos carry no MAC". The app requests and verifies a MAC on every method that carries one, and accepts the message, reaction, roster and request values that `listRecords` returns over TLS from the host the DID document names, as it did before this migration. The prompt authenticates a whole repo by rebuilding the set hash from every `{collection}/{rkey}/{cid}` and comparing it with the MAC-verified commit (`getRepo` as STAR, `listRepoOps`), which the plan lists as out of scope and which a partial-window reader cannot do; the alternative is one MAC-verified `getRecord` per consumed record, an ECDH on both sides for each of up to 20,000 records per channel (the 100-message DM read already costs 4.9 s against a 5 s budget). A MAC proves the response came from the holder of the author's KEM key, which is the author's own host, so neither closes a host forging its own users' records. Recorded as the third consequence in the pin note with the three options: adopt STAR sync, verify only the displayed window, keep the present trust.
    - **Owner decision 2026-10-31, keep and document: departed members' earlier messages** (Codex, important). Writer eviction drops them from a cold-cache history; no cutoff the app can compute is safe, because a record's `createdAt`, TID key and `rev` are controlled by the departed member and their host, and the app keeps no removal timestamp. Pin note, first consequence.
    - *A stricter comparator for the `space:` tokens of a restored DM session* (Codex, minor): the PDS rewrites those tokens, no required `space:` grant changed in this pin, and a comparator that disagreed with the PDS's rewriting would send users through consent in a loop. Revisit when a `space:` grant is added.
    - *Deleting the declaration with the inbox, and reconciling it at startup* (Codex; owner decision 2026-10-31, keep and document): the plan's D2 says the recipient deletes it with the inbox, but no code deletes an inbox, so there is nothing to pair. An inbox removed out of band leaves a stale declaration and a request reads as delivered, because a write into another authority's space is not checked by the sender's host (documented and tested). Reconciling at startup would need a `repo:` delete grant, forcing every existing DM session through consent again, for a case the app cannot produce.
