# M6 — Independence proof and documentation

Read `common.md` and the plan's §1 and §6 (M6) first.

## Tasks
1. **Independent DM reader:** `src/reader/independent-dm.ts`. It is a deliberately separate, minimal implementation that renders a conversation from published lexicons only.
   - It must NOT import anything from `src/dm/`. It may import only `src/protocol/*`, `src/atproto/xrpc.ts`, `src/atproto/record-pages.ts` and `src/atproto/space-credential-core.ts` (the published-protocol layer).
   - Input: an `AtprotoClient` for the user's PDS, a PDS resolver, a key generator, `convKey`, and `participants`.
   - Output: the latest N messages plus their reactions, and per-half status. It must do its own merge; don't reuse `src/dm/merge.ts`.
2. **Parity acceptance:** extend `protocol-tests/dm-acceptance.test.ts`. After the 1:1 and group flows, assert that `DmClient.readConversation` and `readIndependentDmConversation` return identical message URIs, texts, reactions, and half statuses.
3. **"Server off" verification:** confirm that the M4 server-off test covers every flow (enable, each policy mode, start, request discovery, accept, send, edit, delete, react, read, leave, delete everything, re-notify). Extend it where it doesn't. Also add a static check (a unit test that greps the module graph, or an ESLint rule if that's simpler) proving that nothing under `src/app/api/**` imports `src/dm/**`.
4. **Docs.**
   - Update `SPEC.md`: V1 scope now includes DMs (1:1 and group ≤ 100) with the new invariants.
   - Update `ARCHITECTURE.md`: a DM runtime boundary section covering the browser session, no server custody, and the content-free SSE.
   - Update `docs/operations.md`: the DM SSE route and what an operator can and cannot see.
   - Update `PROGRESS.md` with M2–M6 evidence and exact command results.
   - Mark the plan status in `.ai/plans/direct-messages.md` as implemented, noting any deviations.
   - Create `CODE-MAP.md` at the repo root: an architecture overview with ASCII diagrams of the app/server/PDS/browser boundaries, the directory map, entry points, the DM data flow, and conventions. Keep it accurate to the code.
5. **Full verification run** (report every result): `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`, `pnpm test:acceptance`, `pnpm test:browser`, all three pinned-PDS Slack suites, and one `pnpm test:performance` run with the DM performance numbers. The existing channel performance test is slow (~30 min), so run it last and report its timing.

## Done when
Everything above passes and the docs describe the code as it actually is.
