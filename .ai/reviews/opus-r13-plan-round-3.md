## Medium

**M1. The admin role's wildcard space-CRUD scope grants no writes under the pinned scope semantics the plan itself treats as normative.**
plan:85 and plan:187 spell the admin grant as `space:*?action=read&action=create&action=update&action=delete` — with no `collection` parameter — and the parenthetical at plan:85 asserts this is what lets admin sessions pass live narrowing for "modality spaces, and standard account/space migration". Pinned `SpacePermission` matching says otherwise: create/update/delete targets match only via `collectionAllows`, which returns `false` when the grant has no collection (`packages/oauth/oauth-scopes/src/scopes/space-permission.ts:165-170`), and a `collection: "*"` target — which `space.importRepo` checks explicitly (`importRepo.ts:44-46`, mirrored at plan:121) — "is matched only by a grant that covers every collection" (`space-permission.ts:110`). `withDefaultCollections` cannot materialize collections for a wildcard space type. These semantics are normative for `group.opensocial` scope strings: the upstream validator itself matches permission sets with the pinned `SpacePermission.matches` (`scripts/validate-lexicons.mjs:19,240-245`). As written, the bare token contributes read-everywhere and nothing else; admin writes work only where `authManageGroup`, the label grant, or `flockModalityAuthorityScopes()` happen to cover, admin-session `space.importRepo` fails its `collection:'*'` check, and the plan's stated rationale misleads the Wave 2 implementer of `rbac.ts` into either shipping dead scopes or silently deviating from pinned grammar.
**Fix:** change the token to `space:*?collection=*&action=read&action=create&action=update&action=delete` in both the `admin` role (plan:85) and `groupAdminScopes()` (plan:187), and add `@atproto/oauth-scopes` to the `apps/group-host` dependency list (plan:98) so `rbac.ts` parses/matches scope strings with the pinned implementation instead of a re-derivation.

**M2. The hand-rolled OAuth AS still omits redirect-URI validation and single-use authorization-code consumption.**
§3.2.4 (plan:148-154) enumerates PAR, PKCE `S256`, `private_key_jwt`, DPoP claims, `token_type`, and refresh-family CAS, and plan:136 routes client-metadata fetches through `boundedSafeFetch` — but nowhere does the plan require the AS to (a) validate the PAR/authorize `redirect_uri` by exact match against the fetched `client_metadata.redirect_uris` (and redirect only to it), or (b) consume rows of the `oauth_code` table (plan:143) atomically as single-use, binding each code to `client_id`/`redirect_uri`/PKCE challenge and revoking anything issued from a replayed code. Both are OAuth 2.1 MUSTs for an AS, and both were on this round's resolution checklist. Under the plan's own "anything unlisted will silently not exist" standard, the reference host ships as an open redirector whose codes are replayable (PKCE limits exploitability but does not license dropping either control), and every gate still passes since no test asserts them.
**Fix:** add two sentences to §3.2.4: `/oauth/par` + `/oauth/authorize` validate `redirect_uri` by exact string match against the client's metadata `redirect_uris` and redirect nowhere else; `/oauth/token` consumes `oauth_code` in a single atomic delete-returning step keyed to `(code, client_id, redirect_uri, code_challenge)`, with reuse revoking the session family it minted. Add both to the Gate 5 OAuth case list (plan:232).
