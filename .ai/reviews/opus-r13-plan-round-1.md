## High

**H1. Stale `#atproto_space_host` service model, and no service-auth verification spec for the 9 methods — wrong aud conventions will be built.**
Plan §3.1 `plc.ts` (line 180) publishes `#atproto_space_host` in the group's PLC genesis op. That identifier is dead at the pinned commit: the space host is addressed as `<authorityDid>#atproto_pds` (`packages/space/src/credential.ts:16-18` `spaceHostAud()`), and `alpha-migrations/prompt-10-22-26.md:113-120` states the dedicated service entry is gone and receivers "no longer accept `#atproto_space_host`". (The spec repo's `validate-lexicons.mjs:251` matching aud `${group}#atproto_space_host` proves nothing — it passes only because every opensocial rpc permission has `aud: "*"`.) Compounding this, the plan never specifies service-auth verification for `requestJoin`/`cancelJoinRequest`/`leaveGroup`/`createReport` (or the group-session methods): expected `aud` (must be `groupDid` or `${groupDid}#atproto_pds`, mirroring `pds/src/api/com/atproto/space/notifyRepoUpdate.ts:16-31`), `aud === input.group` (otherwise a token minted for group A replays against group B on the same multi-group host), `lxm` binding, `iss` signature via the caller's `#atproto` key, and lifetime bounds (operator precedent: `apps/operator/src/operator/security.ts:76-107`, 75 s default). Likewise inbound `notifyRepoUpdate` (iss = writer DID = body `repo`, signed with the writer's own key) and delegation-token verification (aud `spaceHostAud(groupDid)`, 60 s single-use replay check, `pds/src/auth-verifier.ts:485,497-508`) are unspecified.
**Remediation:** drop `#atproto_space_host` from `plc.ts`; add a "Service auth & audiences" subsection to §3.1 pinning every inbound/outbound aud/iss/lxm/lifetime rule to the pinned conventions, including the client-side aud `@flock/client` will request for the 9 methods.

**H2. The Group Host's `com.atproto.space.*` + repo-host surface is never enumerated — conformance cannot be checked and endpoints will be missed.**
Plan §3.1 describes `repo-store.ts` primitives and the 9 `group.opensocial.*` methods, but the group host must also serve, per the pinned surface (`lexicons/com/atproto/space/`, 30 files): space-host side `authorizeSpaceSync` (unauthenticated endpoint; body-authenticated via delegation token + optional client attestation + `notify` registration with a synchronous `confirmRegistration` challenge round-trip — `pds/src/api/com/atproto/space/authorizeSpaceSync.ts:145-168`), `listWriters`, `getSpace`, `removeWriter`, inbound `notifyRepoUpdate` (hash-only: `data` is an LtHash digest; the host **never pulls writer repos** — syncers pull from each writer's PDS, `space-notifications.ts:457-496`, `lex-space/src/space-reader.ts:778-783`); repo-host side for the group's own repos (including its repo *inside invitees' invites spaces*, which invitee-side syncers pull from the group host): `getRecord`, `listRecords`, `getLatestCommit`, `listRepoOps` (compound `rev/idx` cursor — the plan's `space_oplog` columns match), STAR `getRepo` (`application/vnd.dasl.star`), with full space-credential verification (external authority's `#atproto` key for invites spaces, `cnf.kid` PoP via RFC 9421, `atproto-space-audience` = repo owner's bare DID) and KEM-MAC response signing; plus serving the public repo (`declaration/self`) and outbound `notifySpaceUpdate` with the `#spaceDeleted`/`#registrationExpired` union variants. Migration endpoints (`exportSpaceMeta`/`importSpaceMeta`/`importRepo`, `proposal.md:161-165`) are nowhere mentioned, not even as an explicit deferral. The plan's primitives imply most of this, but a conformance-grade plan for a from-scratch host must state the exact XRPC surface — anything unlisted will silently not exist, and Gate 5 failures will be debugged blind.
**Remediation:** add an explicit endpoint table to §3.1 (implemented / rejected-with-error / deferred-for-migration), including the delegation-token replay cache and `confirmRegistration` flow, and state the migration deferral.

**H3. The `GroupBrowserOAuthClient` isolation mechanism is unimplementable as written with `BrowserOAuthClient`.**
Plan §1.3.1/§4.5/§6 (lines 63, 319, 378) promise a "dedicated browser IndexedDB database … `flock-group-oauth:<viewerDid>`, completely separate from `BrowserOAuthClient`'s `@@atproto/oauth-client-browser(sub)` personal session". At the pin, `BrowserOAuthClient` hard-codes `new BrowserOAuthDatabase()` with DB name `'@atproto-oauth-client'` (`oauth-client-browser/src/browser-oauth-database.ts:71-83`, `browser-oauth-client.ts:127`), explicitly **omits** `sessionStore`/`stateStore` from its options and overrides any passed stores (`browser-oauth-client.ts:23-45,129-147`), does not export `BrowserOAuthDatabase`, and shares the `(sub)` localStorage current-account key and module-level BroadcastChannels across instances on one origin. A second `BrowserOAuthClient` would therefore share storage with the personal session and clobber the current-account pointer — violating the plan's own §6 invariant. The viable path exists but must be specified: instantiate the base `OAuthClient` (re-exported from `oauth-client-browser`) with custom per-viewer IndexedDB `SessionStore`/`StateStore`, a hand-written `RuntimeImplementation` (`WebcryptoKey.generate`, `crypto.getRandomValues`/`subtle.digest`, `navigator.locks`; the library's `BrowserRuntimeImplementation` is not exported), and own callback handling on `/oauth/group-callback`.
**Remediation:** rewrite the `GroupBrowserOAuthClient` section to specify the base-`OAuthClient` composition, the store schemas, and the `signOutAccount(viewerDid)` deletion of the per-viewer DB; add a unit test asserting the personal `'@atproto-oauth-client'` DB and `(sub)` key are untouched by group sign-in/out.

## Medium

**M1. Last-admin `leaveGroup` refusal is an undeclared spec deviation, and the plan has no group-deletion path.** `leaveGroup.json` declares only `GroupNotFound`; `proposal.md:108,233` frames leaving as a personal action. Plan §3.1 rbac item 2 and §6 (line 377) refuse `leaveGroup` for the last admin — so a group's creator can *never* leave (there is no deactivate/delete-group operation anywhere in the plan; `group_account.deactivated_at`/`takedown_ref` columns exist with no method). Define a named error (e.g. `LastAdmin`), document the deviation as host policy (allowed by `proposal.md:114`-style host discretion, but it must be explicit), and give the sole remaining admin an exit (e.g. sole-member leave tombstones the group, or an admin-initiated group deletion flow).

**M2. Space-index scope conflicts with the spec's own example.** Plan §3.1 `repo-store.ts` (line 189) maintains `group.opensocial.space` entries only "when modality spaces are created/deleted", reading `proposal.md:36` narrowly — but `examples/records.json:88-94` contains an index entry for the **meta** space, and `space.json` says the host maintains the index "as spaces are created, deleted, or unlisted" without a modality restriction. Pick the example-conformant behavior (index every space except `members` itself, honoring `unlisted`), test the `unlisted` toggle transitions in both directions, and note the ambiguity in the protocol-feedback doc.

**M3. `createReport` validation requirements are unplanned.** `createReport.json` requires "the caller must be able to read the subject's space", an `InvalidSubject` error ("The subject isn't in this group"), and `labeler.json` declares accepted `reasonTypes`/`subjectTypes`/`subjectCollections` (`proposal.md:145,234`). Plan §3.1 `moderation.ts`/`methods.ts` (line 190) specifies none of these checks. Specify: subject-space membership-read check (policy evaluation for the caller), subject-URI-belongs-to-a-group-space validation, labeler-based report filtering, and the open→reopen transition for resolved subjects.

**M4. Eviction does not revoke outstanding read credentials.** Plan §3.1 covers writer-set eviction (`removeWriter` + `#repoRemoved`) but not credential revocation: pinned space hosts send `com.atproto.space.notifyCredentialsRevoked` to repo hosts, which then answer `CredentialRevoked` (`lexicons/com/atproto/space/notifyCredentialsRevoked.json`). Without it, an ejected member's existing space credentials keep working against member-PDS repo reads for up to the credential lifetime (max 3600 s, default 600 s — `packages/space/src/credential.ts`). Add revocation of group-host-issued credentials plus `notifyCredentialsRevoked` fan-out to writer repo hosts on membership loss.

**M5. `membership.roles` ≤ 100 collides with the per-private-channel role design at the declared envelope.** `membership.json` caps `roles` at `maxLength: 100`; the plan assigns one `channel-<skey>` role per private channel per member (§2.2), and the workspace envelope allows 100 channels (`packages/protocol/src/workspace-summary.ts:10-26`). A member of ~98+ private channels plus `member`/`admin` exceeds the lexicon cap and the membership write fails validation. Document the derived limit, enforce it in the operator `createChannel`/`decideJoinRequest` kinds with a clear error, and add an envelope test.

**M6. Hand-rolled OAuth AS: justify vs `@atproto/oauth-provider`, and pin the client-asserted metadata contract.** The plan builds PAR/authorize/token/DPoP from scratch (§3.1 `oauth.ts`) while the pinned repo ships `@atproto/oauth-provider` (used by the PDS). If hand-rolling stands (defensible given the nonstandard two-sided flow), the plan must pin what the pinned client *requires*: `client_id_metadata_document_supported: true` is mandatory (`oauth-authorization-server-metadata-resolver.ts:124-128`), issuer must round-trip exactly (`verifyIssuer`, `oauth-server-agent.ts:194-209` — this also means the PLC `#atproto_pds` endpoint, protected-resource `resource`, and AS `issuer` must all be the identical canonical origin, and **PLC registration must complete before the authorization code is redeemable**, since the client re-resolves the new group DID during the token callback), token response `token_type: "DPoP"` with `scope` containing `atproto`, `iss` param behavior consistent with `authorization_response_iss_parameter_supported`, and `token_endpoint_auth_methods_supported` covering `none` + `private_key_jwt`. DPoP nonces may be omitted (client treats them as optional). Also specify the group host's own outbound fetch policy (`safeFetchWrap`-equivalent for DID-doc-derived endpoints, upstream PDS metadata, and client-metadata fetches — it is an SSRF surface just like the PDS).

**M7. Post-leave personal-PDS residue breaks discovery.** Discovery (§4.2) lists `group.opensocial.members` spaces via the member-PDS `listSpaces` ("spaces the account has written to or is authority for"). After `leaveGroup`, the member's PDS still holds their space repo (acceptance record) for that space; the plan hedges ("deletes local acceptance/self if desired", line 268). Whether `com.atproto.space.deleteRecord` even completes cleanly once the group host refuses the eviction-rejected `notifyRepoUpdate` is unverified. Specify the exact cleanup mechanism (and its failure mode when the host refuses the notify), and add an acceptance test that a left group disappears from `discover()`.

## Low

1. **Lexicon arithmetic slop** — plan line 90/97 says "22 lexicons", then "3+8+2+4+9=26?", then corrects to 27; the itemized list is right, the lead-in numbers are wrong. Fix the text.
2. **Redundant scope + inbox-read ambiguity (§4.1)** — at the pin, `action=read` is collection-independent (`space-permission.ts:136-163`), so the spec's `authParticipate` already grants full members-space read and the plan's extra `space:group.opensocial.members?…&action=read` scope is redundant (harmless; state it's intentional). Conversely the `new.flock.inbox` member scope omits `action=read`, and reads are *not* implied by write actions — include `read` for everyone and let `group.opensocial.policy` gate actual access, resolving the "(plus action=read for admins)" hedge.
3. **`applyLabel` sketch omits required `cts`** (`label/record.json` requires `uri`,`val`,`cts`), and the "duplicate `(uri, cid, val)` → latest `cts` wins" rule from `prompt-11-12-26.md:236` should be in `evaluateSpaceLabels`.
4. **Test logistics** — `test:acceptance`/`test:browser` are hand-maintained allowlists in the root `package.json` (new `opensocial-groups.test.ts` must be added there); `reconcile-workspaces.test.ts` and the `reconcile` script need removal with the `reconcileWorkspace` kind; `opensocial-lexicons.test.ts` imports pinned-checkout dists, but Gate 3's plain `pnpm test` sets no `ATPROTO_PIN_CHECKOUT` — define its resolution/skip behavior.
5. **CODE-MAP.md** (428 lines, exists) is not in Wave 6's deliverables despite a new app, deleted lexicons, and ownership moves — add it.
6. **`pendingMembers` must exclude `app-*` accounts** (apps never write `acceptance`, §2.2 line 147), or every bot shows as pending forever.
7. **`meta` `publicRead: true` unconditionally** (§2.2 line 132) makes every workspace name/description public, including invite-only ones — consider a creation-time option.
8. **Blobs unaddressed** — `profile.json` allows `avatar`/`banner` blobs; the group-host schema has no blob storage. Declare avatars unsupported in Flock's UI for R13 or add blob tables + `getBlob`.
9. **`requestJoin` idempotency** for an existing member is undefined — return `admitted` with the existing membership ref.
10. **Prod NSID resolution dependency** — `include:` expansion and member-PDS validation of `group.opensocial.*` space types require lexicon resolution; tests use `lexiconAuthority`, but production depends on the `opensocial.group` domain publishing the schemas — document the external dependency (and keep spelled-out scopes as the default, as the plan already does).
