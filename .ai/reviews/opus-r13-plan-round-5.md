## Medium

**M1. The genesis op cannot be built "via `atprotoOp`" with an `atproto_kem` verification method — the named API doesn't accept one, and the obvious compile-clean workaround silently drops the KEM key.**
plan:192 instructs building the signed genesis op "via `atprotoOp` + `didForCreateOp` from `@did-plc/lib` (`rotationKeys: […]`, `verificationMethods: { atproto, atproto_kem }`, `alsoKnownAs: […]`, `services: { atproto_pds: … }`)". The real export is `atprotoOp(opts: { signingKey, handle, pds, rotationKeys, prev, signer })` — it accepts no `verificationMethods`/`services`/`alsoKnownAs` inputs and hardcodes `verificationMethods = { atproto }` before signing (verified in the pin's `@did-plc/lib` 0.0.1 and 0.0.4 `operations.d.ts`). Signing happens inside the call, so the KEM method can't be appended afterward without invalidating the signature and the derived DID. An implementer who simply drops the unsupported fields gets a *compiling, PLC-valid* genesis op whose DID doc lacks `#atproto_kem` — contradicting plan:21, breaking every HPKE KEM-MAC read (plan:145) and the migration-time `#atproto_kem` check (plan:130); the failure only surfaces deep in Gate 5. The pinned PDS itself never calls `atprotoOp` for this: its pattern is `formatAtprotoOp({ …, prev: null })` → `unsigned.verificationMethods.atproto_kem = kemKey` → `signOperation(unsigned, signer)` → `didForCreateOp(op)` (`packages/pds/src/util/plc.ts:17-20`, `createPlcOp`, used by `createAccount.ts:347`).
**Fix:** in plan:192, replace "`atprotoOp` + `didForCreateOp`" with "`formatAtprotoOp` (then set `verificationMethods.atproto_kem = kemKey.did()`) + `signOperation` + `didForCreateOp`, mirroring pinned `createPlcOp` (`util/plc.ts:17-20`)".

**M2. The refresh-token grant is specified to require `Authorization: DPoP <token>`, which contradicts the plan's own `ath` rule, the pinned provider, and every standard ATProto client.**
plan:185: "`/oauth/token` (`refresh_token`) **and** all resource routes require `Authorization: DPoP <token>` … and `proof.jkt === session.dpop_jkt === payload.cnf.jkt`." A refresh request carries the refresh token in the body (`grant_type=refresh_token`), sends no `Authorization` header, and presents no access JWT — so `payload.cnf.jkt` is undefined there, and plan:183 itself forbids `ath` on `/oauth/token`, which is incoherent with presenting a DPoP-bound token in `Authorization` on that route (RFC 9449 §4.3 would then require `ath`). Plan:179's `token_endpoint_auth_methods_supported: ["none","private_key_jwt"]` leaves no role for an `Authorization` header at the token endpoint either. `@atproto/oauth-client` (the exact client `GroupBrowserOAuthClient` is built on, plan:30) refreshes with only a DPoP proof header — a literal implementation 401s every refresh, making Gate 5's long-lived-session flows unpassable; the self-contradiction will stall or mis-steer the Wave 2 implementer in the most security-sensitive section.
**Fix:** split the sentence: "`/oauth/token` (`refresh_token`) requires a DPoP proof with `ath` absent and `proof.jkt === oauth_session.dpop_jkt` for the presented refresh token's family (no `Authorization` header); all resource routes require `Authorization: DPoP <token>` (rejecting `Bearer`) and `proof.jkt === session.dpop_jkt === payload.cnf.jkt`."
