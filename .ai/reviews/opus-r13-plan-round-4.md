## Medium

**M1. The `prompt=create` bootstrap no longer specifies any `grants` for the two core-space policies — a Rev 4 regression that contradicts the plan's own `isEffectiveAdminMember` predicate and breaks acceptance sync at birth.**
Rev 3 stated the creator gets `members/self` write "so `acceptance/self` syncs" (confirmed in Round 3's audit); Rev 4's compressed step 3 (plan:181) now creates `meta/self` (`publicRead: publicMeta, unlisted: false`, `profile/self`, `labeler/self`) and `members/self` (`publicRead: false, unlisted: false`, roles + `membership/<creatorDid>`) with **no `grants` arrays** for either `group.opensocial.policy`, and no other section supplies them. Taken literally: no role holds `read`/`write` on `members/self`, so (a) member-authored `acceptance/self` never enters the writer set and never syncs (plan:20/38; proposal.md:123 — "write to `members`, so its acceptances sync"), and (b) `isEffectiveAdminMember` clause (b) (plan:200) is false for everyone, so the group is born with zero effective admins and the very first `membership` put (inviting anyone) is rejected `400 LastAdmin` (plan:201). A repair path exists (`updateSpace` on `members/self` passes post-state `LastAdmin`), but the implementer must invent the bootstrap values, and Gate 5's admission/acceptance/LastAdmin tests all fail until they do.
**Fix:** spell the bootstrap grants in plan:181: `members/self` → `grants: [{role:"admin", read:true, write:true}, {role:"moderator", read:true}, {role:"member", read:true, write:true}]`; `meta/self` → `grants: [{role:"admin", read:true}, {role:"member", read:true}]` (reads matter when `publicMeta=false`; group-DID authorship needs no `write`). Note that clause (b) of `isEffectiveAdminMember` is then satisfied by the admin grant directly rather than via the member role.

**M2. `pending_plc` journal rows have no startup recovery, so a crash in the PLC-submission window orphans an unrecoverable DID and permanently wedges the handle.**
Step 1 persists the journal as `status='pending_plc'` before calling `PLC_URL` (plan:179) and step 2's idempotency note covers only in-flow retries (plan:180); the startup/compensation path is defined **only** for stale `plc_published` rows (plan:182). If the process dies after the PLC POST lands but before `status` is updated (or before submission, leaving a dead reservation), the row stays `pending_plc` forever: no tombstone, `handle_reservation` never released — exactly the "failpoints before and after PLC submission" residue Codex R3 H6 required closed, and the Gate 5 pre-PLC failpoint test (plan:266) has no specified recovery behavior to assert.
**Fix:** one sentence in plan:182: on startup, also process stale `pending_plc` rows — derive the DID from the journaled `genesis_op_json` (`didForCreateOp`), probe `PLC_URL/<did>` via `boundedSafeFetch`; if the genesis op is present treat the row as `plc_published` (tombstone-compensate), otherwise release `handle_reservation` and mark `status='compensated'`.

**M3. The PLC toolchain is fabricated/undeclared: `plc.createTombstoneOp` does not exist, and `@did-plc/lib` is absent from the group host's "complete" direct-dependency list.**
Plan:182 instructs "signs & submits a PLC tombstone operation (`plc.createTombstoneOp`)", but `@did-plc/lib` (0.0.1 and 0.0.4 in the pin) exports `tombstoneOp(prev: CID, key: Keypair)` — no `createTombstoneOp` — and the pinned PDS itself uses `ctx.plcClient.tombstone(did, rotationKey)` (createAccount.ts:156). Worse, plan:114's exhaustive dependency list omits `@did-plc/lib` entirely, yet `src/plc.ts` needs PLC op construction in three places (genesis op signing in step 1, tombstone compensation in step 4, and the `signPlcOperation` route's rotation-key signing). Under pnpm's isolated `node_modules`, undeclared imports fail outright. (`@atproto/common` — needed for `TID.fromStr` at plan:144 — and `@atproto/syntax` are likewise missing from the direct list.)
**Fix:** add `@did-plc/lib` (and `@atproto/common`, `@atproto/syntax`) to plan:114; in plan:179/182 name the real APIs — `atprotoOp`/`didForCreateOp` for genesis, `signOperation`/`assureValidOp` for the signing route, `tombstoneOp(prevCid, rotationKey)` for compensation — submitting ops via `boundedSafeFetch` POST rather than the lib's built-in client transport.

**M4. The 19,163-file aggregate digest constant cannot be reproduced from the plan's stated formula, so Gate 1 is unimplementable to green as written.**
The file set is right (exactly 19,163 files; zero dotfiles, so glob and `find` agree) and every sibling constant in plan:6-8 verified byte-for-byte — but the aggregate `2ecad4ac…f681d5` does not emerge from "`sha256` over `relPath + "\0" + sha256(bytes)`" sorted lexicographically under **any of ten natural interpretations** I computed over the actual pin (hex-concat, newline-terminated, newline-joined, raw-digest bytes, hex-first, per-entry digest-of-digests in binary and hex, pre-sorted entry strings, `sha256sum`-style lines, prefix-stripped paths).
