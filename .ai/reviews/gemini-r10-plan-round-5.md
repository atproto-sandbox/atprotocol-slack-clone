### 3. Security

- **BLOCKING** (`verified`) — **Plan section:** `## Design → ### The webhooks app` ([.ai/plans/r10-interactions-progress.md:247-255](.ai/plans/r10-interactions-progress.md#L247-L255), [:265-266](.ai/plans/r10-interactions-progress.md#L265-L266)), `## Steps → ### R10c` ([:355](.ai/plans/r10-interactions-progress.md#L355), [:360](.ai/plans/r10-interactions-progress.md#L360)).
  - **Code:** [packages/deployment/src/security-headers.ts:26-35](packages/deployment/src/security-headers.ts#L26-L35), [:41-50](packages/deployment/src/security-headers.ts#L41-L50); [apps/operator/src/operator/server.ts:54-68](apps/operator/src/operator/server.ts#L54-L68), [:131-133](apps/operator/src/operator/server.ts#L131-L133); [.ai/plans/platform-refactor.md:900](.ai/plans/platform-refactor.md#L900); [CODE-MAP.md:288-289](CODE-MAP.md#L288-L289).
  - **Why wrong/missing:** The webhooks admin page's CSP, cookie attributes, and test gate combine to break sign-in in real browsers while passing Node tests:
    1. **Zero-JS ATProto OAuth redirect violates `form-action 'self'` in Chromium and WebKit.** Lines 265–266 lock the exact header `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; form-action 'self'; frame-ancestors 'none'` with zero JavaScript. Unlike `apps/web` (`security-headers.ts:28`, `platform-refactor.md:900`, where sign-in and the authority flow are JS navigations, not HTML form submissions) and `apps/operator` (`security-headers.ts:33`, which omits `form-action`), a zero-JS admin sign-in page must submit the typed handle/DID via an HTML `<form>`. When the server responds with a `302`/`303` redirect to the account's PDS authorization URL (a different origin, even on loopback ports), Chromium and Safari enforce `form-action 'self'` across the form's redirect chain (CSP3 § 6.9.2) and block the redirect.
    2. **`SameSite=Strict` on a cross-site OAuth callback redirect withholds the cookie.** First, the 10-minute flow-binding cookie (`:250`) must be `SameSite=Lax` (matching `server.ts:132`), because browsers withhold `SameSite=Strict` cookies on the cross-site PDS → `/admin/oauth/callback` redirect. Second, when `/admin/oauth/callback` sets the `SameSite=Strict` session cookie (`:253-254`) and `302`/`303`-redirects to `/admin`, the redirect chain `[PDS → /admin/oauth/callback → /admin]` remains cross-site (RFC 6265bis § 5.2), so browsers withhold the `SameSite=Strict` session cookie on `GET /admin` and show the signed-out page.
    3. **R10c's Node `acceptance` gate (`:360`, `CODE-MAP.md:288-289`) does not enforce CSP or browser `SameSite` redirect-chain rules,** so both failures pass every planned unit and acceptance test.
  - **Recommended change:**
    1. Either answer the sign-in `<form>` submission with a `200` HTML page carrying an `<a href="<authorizeUrl>">` link (keeping `form-action 'self'` on every response), or allow `form-action 'self' https:` (plus `http://127.0.0.1:*` in loopback dev, matching `security-headers.ts:49`) on the unauthenticated sign-in page while keeping `form-action 'self'` on the authenticated admin page.
    2. Specify `SameSite=Lax` on the 10-minute flow-binding cookie, and either render a `200` response directly from `/admin/oauth/callback` (so the next navigation is same-site and sends the `SameSite=Strict` session cookie) or use `SameSite=Lax` on the session cookie (all state changes are already `POST`-only with CSRF token + `Origin`).
    3. Exercise the admin sign-in flow in R10c's gate via Playwright Chromium (`test:browser`) rather than Node-only `fetch`.
