# Pinned PDS conformance tests

These tests are written to run inside the pinned `bluesky-social/atproto` checkout so they can use its real PDS test network, test actors, lexicons, and OAuth provider. They are not app tests. Their source pin and setup commands are in [the protocol pin note](../../docs/protocol/atproto-spaces-pin.md).

Apply [`strict-credential-expiry.patch`](./strict-credential-expiry.patch) to the pinned `5b95b2f2` PDS checkout (SHA-256 `e9cfae5beb29d01c494087abf79eaf58fd48312956422c91ff29a405977aae3f`) before building it; verify its SHA-256 against the pin note. This local overlay removes clock tolerance for space credentials only, preserving the allowance for delegation and client-attestation timing. Copy the three test files into the pin's `packages/pds/tests/space/` directory, then run the commands listed in the pin note from the atproto monorepo root. Each custom test file sets an isolated `TMPDIR` before creating its PDS network and removes that root after `network.close()`, because the pinned `TestPds.close()` stops servers without deleting their data and blob directories. The authority test publishes a temporary `org.slack.workspace` space lexicon to the fixture's lexicon authority; it does not modify PDS or dev-env source. The DM test (`slack-dm-conformance.test.ts`) is the DM plan's M0 gate; its observed behaviors are asserted, so protocol drift fails the suite. The inbox test simulates lost notifications by making the writer PDS unable to resolve the authority DID for the duration of one request.

The inbox recovery test intentionally demonstrates that `listRepos` alone cannot recover a PDS-to-authority `notifyWrite` loss. It reads the candidate DID from owner-only `listMembers`, then proves the admin's inbox space credential can read that repo. The production `listInboxWriters` operator method will expose only this candidate DID list to a verified active admin; the admin app fetches request records directly from PDS.

## App acceptance harness

From the app checkout, run the two-host app flow and process-restart journal recovery against the pinned checkout:

```sh
PATH=/path/to/node-v22.17.0/bin:$PATH ATPROTO_PINNED_CHECKOUT=/path/to/atproto-spaces-phase1 pnpm test:acceptance
```

The harness starts two real local PDSes, creates accounts on both, then exercises backend bootstrap, operator mutations, workspace discovery, public-channel paging, private request denial, fresh-generation resubmission, stale approval rejection, current-generation approval, private roster/message reads, inbox credential recovery after a dropped writer notification, removal semantics, and bounded journal retries. The recovery path creates an online SQLite backup, restores it to a separate path, resumes the pending operation in a new process, rediscovers the workspace, and reconciles PDS membership. That subprocess restores a PDS-issued, DPoP-bound Node OAuth session from the encrypted store; `AUTH_ENCRYPTION_KEY` is supplied separately from the backup. A live Next server test also verifies the web-session cookie rejects anonymous requests and authorizes workspace bootstrap through the restored session. The session is constructed directly, so the test does not complete the browser authorization-code callback. Exact OAuth scopes and service-auth claims remain covered by the pinned PDS OAuth conformance suite above.

## Full supported-size workload

Run the scale workload against the same pinned checkout:

```sh
PATH=/path/to/node-v22.17.0/bin:$PATH \
ATPROTO_PINNED_CHECKOUT=/path/to/atproto-spaces-phase1 \
pnpm test:performance
```

After one workspace bootstrap, it performs a journaled invite at the 200-member boundary, then directly seeds the remaining channel directories, membership records, messages, and reactions through the pinned PDS APIs. It provisions 200 logical workspace members across two PDSes, creates 100 channels (99 public and one private), and targets 20,000 messages plus 20,000 reactions in every channel. It scans all 199 inbox writer candidates and checks exact latest-100 message and reaction equality through both the stateless independent reader and the primary cache path. The passing 2026-09-25 run covered messages only: 2 million message writes, 199 explicit writer repos, latest-100 message URI/content equality, and inbox recovery below 60 seconds. It wrote zero reactions, so it does not establish reaction-envelope or reaction-parity behavior. Its measured timings were: account provisioning 6.181 seconds, direct membership setup 76.139 seconds, journaled invite 1.330 seconds, journaled channel creation 2.544 seconds, private request write 0.039 seconds, message writes 932.315 seconds, inbox writer reconciliation and candidate-repo reads 1.721 seconds, independent latest-100 read 1.936 seconds, primary latest-100 read 5.197 seconds, public-to-private transition 2.806 seconds, and archive 2.741 seconds. A 2026-09-26 reaction-complete run wrote all 2 million messages and 2 million reactions, and the independent reader returned the latest 100 reactions, but it failed because a full final PDS page cursor was treated as overflow at exactly 20,000 records. Primary-reader checks, parity, and the final report were not reached. Both readers now probe one record beyond the boundary; typecheck, focused lint, and all 67 app unit tests pass. The full post-fix receipt is recorded below. The retry wrote all messages and 400,000 reactions across 20 channels before free space fell to 8.2 GiB and the run was interrupted. Its isolated fixture root remained after interruption and was removed after confirming all PDS processes had exited and `lsof` found no open handles. A prior reaction attempt stopped after 400,000 messages across 20 channels at 776 MiB free space without writing reactions; its closed fixture root was removed. An earlier attempt stopped during PDS startup with `SQLITE_IOERR_SHMSIZE` before measurements. The test does not measure every lifecycle operation at this envelope; other timings have no PRD latency threshold. The post-fix `pnpm test:performance` run passed on Node 22.17.0. It wrote 2 million messages and 2 million reactions across 200 logical members and 100 channels, verified all 199 inbox-writer candidates, and passed exact latest-100 message and reaction parity through both readers with non-degraded exact-cap scans. Timings included message writes 767.123 seconds, reaction writes 707.621 seconds, independent latest-100 read 15.477 seconds, and primary latest-100 read 43.543 seconds; the full run took 1,642.119 seconds. Available space was 249 GiB at start, at least 243 GiB during the run, and 251 GiB after normal fixture cleanup; no `slack-performance-fixture-*` roots remained. Earlier failed and interrupted attempts above remain historical. Full metrics are in the [implementation plan](../../docs/prd/atproto-slack-implementation-plan.md).

The fixture disables the PDS rate-limit bucket and is not a production-rate-limit or deployed-performance result.
