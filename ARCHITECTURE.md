# Architecture

## Runtime boundaries

- **Browser client:** holds the member's one OAuth session (sign-in is the browser's own flow; `apps/web/src/browser/session.ts`), reads every space through the engine (`packages/client/src`) into the account's IndexedDB store, writes to the member's own repo, and calls the operator with service tokens. It never holds the workspace authority grant.
- **Next.js server:** serves the application UI and hosts the workspace authority operator (its XRPC methods, the authority flow and its callback). It holds no member session, no member token and no member record: it has no member routes, and the sign-in completes in the browser. Browser input is treated as untrusted.
- **PDS spaces:** hold the durable interoperable workspace, inbox, channel, roster, request, decision, message, and reaction state. Their member lists enforce reads.
- **Operator journal:** SQLite persists operation identity, canonical request hash, target state, completed step markers, status, and audit events. It is not a membership or role source. Authority OAuth session material is encrypted at rest with AES-256-GCM using a deployment key.
- **Independent reader:** a separate package consumes only published lexicons and protocol clients; no imports from application database/cache code.

## Data flow

1. A member signs in through atproto OAuth in the browser, with one grant (`memberGrantScopes` in `packages/protocol/src/scopes.ts`): every workspace, inbox and channel space the member lists admit them to, the collections a member writes, the operator's methods (including `new.flock.operator.getDmNotifyTarget`, with pre-R12 sessions lacking it kept valid for reads and polling in `apps/web/src/browser/session.ts`), and the DM set. The authorization code returns in the URL fragment and the tokens stay in the browser's IndexedDB. The workspace authority grant is separate: only the authority flow (`apps/operator/src/operator/authority-grant.ts`) writes it, and signing in or out never touches it.
2. For reads, the browser exchanges a PDS delegation token through `com.atproto.space.authorizeSpaceSync` (`credentialKey`, optional inline `notify: { endpoint, token }` bound to `exp`, returning `{ credential, spaceRev? }`) for a space credential bound to its own non-extractable signing key (ten minutes by default, one hour at most). Every request made with it carries an RFC 9421 HTTP message signature (`createSpaceSigHeaders`, `tag="atproto-space-credential"`) over the credential and its audience, and commit/record reads (`getRecord`, `getLatestCommit`, every page of `listRepoOps`, and `getRepo` `application/vnd.dasl.star`) request ephemeral HPKE MACs (`Accept-Signature`, `info: "atproto-mac"`) verified via `Atproto-Space-Commit` / `Atproto-Space-Record` + `Signature-Input` + `Signature`. The engine syncs writers (`com.atproto.space.listWriters`) and their records from each selected space, validating author, schema, key, and same-channel references.
3. The browser follows its spaces through the operator's change feed and reads a space again when the feed names it.
4. For admin actions, the client obtains a `com.atproto.server.getServiceAuth` JWT with the operator DID service ref as `aud` and the exact method NSID as `lxm`. The operator verifies all claims and re-reads current authority records and PDS member lists before acting. The same kind of token, valid fifteen minutes and reused across polls, authenticates `new.flock.operator.getChanges`, the change feed a client without a cookie follows: it says only which followed spaces changed (each with its own cursor), which the caller may not follow (`denied`, decided from the space's member list read with the authority grant), and which to sync again (`reset`). The operator registers its own inbound webhook sink (`com.atproto.space.confirmRegistration` and `com.atproto.space.notifySpaceUpdate`, authenticated in constant time by token) inline via `authorizeSpaceSync` using one stable token per space (`notification_registration.{token, renew_at, last_space_rev}`), renewing due spaces via a 60-second SQL-first loop (`15 s -> 2 min` failure backoff) alongside a 30-minute discovery sweep, reconciling missed writes via `spaceRev`, and confirming `#spaceDeleted` through authority `authorizeSpaceSync` before purging state.
5. The operator journals the desired state and applies resumable PDS membership (`com.atproto.memberspace.putMembers` / `removeMembers` in batches of `<= 100`) and authority-record writes. It completes only after read-back reconciliation; if the authority account is temporarily suspended (`401 AccountTakedown` or `AccountDeactivated`), the operator preserves the encrypted `authority_grant` without retry storms.
6. Inbox clients reconcile `listWriters` (`#repoWrite` / `#repoRemoved` with a 72-hour full-reconciliation fallback) and owner-authorized `listInboxWriters` at least once per minute, then fetch candidate request records directly with their own inbox credential.

## Storage rules

- The server's SQLite tables are limited to the workspace authorities' encrypted grants and flow state, the operation journal, audit history, workspace/channel/inbox/extension notice registrations (`notification_registration` + `notification_registration_failure`) and content-free change notices (`space_notification`). Zero DM rows are ever stored in any SQLite table. A database from before R6c drops the member session and cache tables and is rebuilt (`apps/operator/src/lib/db.ts`).
- Never persist a locally authoritative member/admin ACL.
- Message/request ownership remains in the member's PDS repo. The operator never reads or proxies request bodies.
- The account's copy of what it reads lives in its browser store (`packages/client/src/indexeddb-store.ts`), one store per account. When the authority refuses a private space credential (the account lost access) or reports the space deleted, stop sync and remove that account's cached copy of the space. A failure to renew for any other reason — including temporary authority suspension (`RepoTakendown` or `RepoDeactivated` on `authorizeSpaceSync` / `listWriters`) — says nothing about the space and keeps the copy.
- The copy of an individual non-authority writer (`repo !== authorityDid`) goes when that writer's repo is permanently unreadable (`RepoDeactivated`, `RepoTakendown`, `SpaceKemError` / `SpaceMacError` / `SpaceRepoVerificationError`, or oversized), when the account signs out (its store is deleted), when another account starts in the same browser (a store another account left behind is deleted first), and at start-up for a space not opened for 30 days. When the space authority's own repo (`repo === authorityDid`) returns `RepoTakendown` or `RepoDeactivated`, sync classifies it as transient authority suspension and preserves cached authority records until recovery, just as for a writer whose host is merely down or whose DID cannot be resolved.
- None of the workspace/channel cache rules above place DM data on the server, and DM state lives in its own browser store; see "Direct-message runtime boundary" below.

## Protocol compatibility

The protocol adapter isolates the draft `com.atproto.space.*` lifecycle, record, writer-set (`listWriters`), oplog (`listRepoOps` with signed commit + MAC on every page and `RepoNotFound`), STAR archive (`getRepo` `application/vnd.dasl.star` via `@atproto/star`, `writeRepoStar`, CID-less `starEntryBytes`), and credential (`authorizeSpaceSync`) APIs plus the batched `com.atproto.memberspace.*` (`putMembers`, `removeMembers`, `listMembers`) and `com.atproto.managedspace.checkAccess` APIs (every Flock space is governed by `packages/protocol/src/atproto/space-policy.ts`, and account-authenticated space/memberspace endpoints enforce `ACCESS_FULL` against app passwords while `com.atproto.server.getServiceAuth` remains permitted). A credential is minted via `authorizeSpaceSync`; every request that presents it is signed with `createSpaceSigHeaders` (`@atproto/space`), and `packages/protocol/src/atproto/space-credential-core.ts` is the single owner of ephemeral HPKE MAC requests and throwing verification (`SpaceKemError`, `SpaceMacError`, `SpaceRepoVerificationError`). The implementation is pinned to `bluesky-social/atproto#5187` commit `6747610566eee1b6d743617bd8eb1136adccb362` (`../atproto-spaces-r12`), npm snapshot `0.0.0-spaces-alpha-20261117141222`, and the rebased strict-expiry patch in `docs/protocol/atproto-spaces-pin.md`. Production `OPERATOR_URL` must be a public HTTPS origin because PDS `safeClient` SSRF protection blocks private/loopback webhook targets unless `devMode: true` and `disableSsrfProtection: true` (`L7`), and production OAuth consent deployments must republish the updated Flock space (`"title"`) and permission/operator lexicons (`L8`). Proposal 0016 is still draft; any pin drift blocks release until the conformance suite passes again.

## Direct-message runtime boundary

DMs are person-scoped, not workspace-owned, and no app-operated component can read, gate, lose, or hold hostage one (`.ai/plans/direct-messages.md` §1). This is a stricter boundary than channels, held entirely by process and import isolation, not by policy alone:

- **One browser-held OAuth session.** `apps/web/src/browser/session.ts` dynamically imports `@atproto/oauth-client-browser` (so it never reaches a server bundle) and constructs a public OAuth client (`token_endpoint_auth_method: "none"`) whose metadata (`apps/web/src/browser/client-metadata.ts`, served at `/oauth/client-metadata.json`) requests the one grant, of which `DM_BROWSER_SCOPES` is the DM part. Its DPoP keys are non-extractable WebCrypto keys and it is stored in the browser's IndexedDB. Pre-R12 sessions lacking `new.flock.operator.getDmNotifyTarget` are still admitted by `restoreSession` (falling back to polling while flagging optional reconnect). The server holds no member session at all; its only OAuth grants are the workspace authorities' grants to its operator, which carry no DM scope (`packages/protocol/src/scopes.test.ts`).
- **The isomorphic engine, `packages/client/src/dm/dm-client.ts`.** `DmClient` is constructed with injected transports (`memberClient`, `resolvePds`, `fetchEndpoint`, `generateKey`, `store`) so the identical class runs in the browser (production) and in Node (unit tests, `protocol-tests/dm-acceptance.test.ts`, `protocol-tests/dm-performance.test.ts`) against a fake or the real pinned PDS. It shares `packages/protocol/src/keys.ts`, `packages/protocol/src/registry.ts`, `packages/protocol/src/atproto/space-key.ts`, `packages/protocol/src/atproto/space-policy.ts`, `packages/protocol/src/atproto/kem-key.ts`, `packages/protocol/src/atproto/space-credential-core.ts`, `packages/protocol/src/atproto/xrpc.ts`, and `packages/protocol/src/atproto/record-pages.ts` with the server's channel code. It lives in `@flock/client`, which depends on `@flock/protocol` only, so it cannot import the operator, its database, its configuration or its OAuth client (`import/no-extraneous-dependencies` in `eslint.config.mjs` holds each package to its `package.json`); it typechecks with no Node types, and lint refuses a Node built-in in it.
- **No server routes, SQLite rows, or cache for DM content.** The server has no member routes and stores **zero** DM rows across every SQLite table (`space_notification`, `notification_registration`, `notification_registration_failure`, `authority_grant`, `member_list`, `oauth_session`). For optional low-latency push wakeups, `DmClient.watch` calls `new.flock.operator.getDmNotifyTarget` with a service token plus a valid `SpaceCredential` and RFC 9421 key-possession proof (`verifyCredentialSig` over `cnf.kid` + short-lived replay guard; the operator never holds the `cnf.kid` private key) to obtain a deterministic stateless `dm1` HMAC webhook token derived from `AUTH_ENCRYPTION_KEY`, then passes `notify: { endpoint, token }` to `authorizeSpaceSync` (immediately falling back to `authorizeSpaceSync` without `notify` if `getDmNotifyTarget`, `confirmRegistration`, SSRF, or `ScopeMissingError` fails so DM reads never block on operator availability). Inbound DM `notifySpaceUpdate` callbacks update only an ephemeral process-local wake ring (`apps/operator/src/operator/dm-feed-wakes.ts`) merged into `new.flock.operator.getChanges` (emitting `reset` across operator restarts, and returning HTTP `400` on DM `#registrationExpired` so PDS `abandonSyncerNotice` drops closed browser tabs immediately); see "Direct messages: what an operator can and cannot see" in `docs/operations.md` for residual in-memory/access-log metadata exposure.
- **Independent second-app parity, `packages/reader/src/independent-dm.ts`.** A separate reader that reconstructs the same conversation (messages, reactions, per-half status) from the `new.flock.dm.*` lexicons alone, sharing only the protocol layer above and never importing `packages/client/src/dm/**` (`@flock/reader` depends on `@flock/protocol` and `@atproto/{space,star,lex-data,lexicon}`, and lint holds it to that) or the engine's sync core (`packages/client/src`; it implements its own full-history merge). `protocol-tests/dm-acceptance.test.ts` asserts this reader and `DmClient.readConversation` return identical state for the 1:1 and group flows, including every per-half status (`ok`, `missing`, `deleted`, `revoked`).
- **Data flow for a DM read:** browser DM session → `mintSpaceCredentialWith` exchanges a delegation token (signed by the browser session) via `authorizeSpaceSync` for a space credential bound to a non-extractable WebCrypto signing key at each participant's own PDS (never blocked if optional `notify` registration is unavailable) → the engine reads and validates each half's header/messages/reactions directly from that PDS → the engine's sync core (`packages/client/src/sync.ts`) checks each half's revision (`listWriters`), lists only halves that moved, and merges them into the latest-N page. No step requires this app's server.
