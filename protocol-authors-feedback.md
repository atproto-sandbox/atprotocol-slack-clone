## 1. What We Built

We built **Flock**, a full-featured Slack-style team collaboration app with a Linear-style collaborative Tasks extension and sovereign 1:1 / group Direct Messages, specifically to stress-test **ATProto permissioned spaces** and **`opensocial.group` atmospheric groups** under realistic product, security, custody, moderation, migration, and scale constraints:

- **Reference `opensocial.group` Group Host (`apps/group-host`, `42` SQLite tables):** Implements `1 Group == 1 did:plc:...` accounts publishing `#atproto`, `#atproto_kem`, `rotationKeys`, and `#atproto_pds` (plus `#opensocial_group` on the host's `did:web` document), a signed `@atproto/repo` MST public repository (`declaration/self` when `publicMeta === true`), core spaces `group.opensocial.{meta,members}/self`, Flock modality spaces (`new.flock.{workspace,inbox}/self`, `channel/<skey>`, `app.inbox/<appSkey>`, `ext.tasks/<tasksSkey>`), flat union RBAC (`group.opensocial.policy` + `effectiveMemberPermissions`), a two-sided ATProto OAuth 2.1 Authorization Server (`prompt=create`, `/oauth/confirm-action`, `recovery` sessions, and sovereign `rotationKeys` `/group-admin/controller-session`), cross-PDS `invites/self` delivery tracking, all 9 `group.opensocial.*` join/moderation XRPCs, pre-tombstone zero-residue `deleteAccount`, and two-GroupHost Standard + Coordinated v1 migration (mirrored 1-for-1 in `@flock/testing` via `group-host-parity.test.ts`).
- **Browser-direct verified sync & dual browser OAuth (`@flock/client`, `apps/web`):** Users hold a personal PDS OAuth session (`session.ts`) alongside isolated per-viewer Group-DID OAuth sessions (`GroupBrowserOAuthClient` in `group-session.ts`, backed by base `OAuthClient` and `flock-group-oauth:${viewerDid}` IndexedDB). The browser mints key-bound `Atproto-Space-Credential` tokens (`authorizeSpaceSync`), writes member records directly to the user's personal PDS, and verifies **RFC 9421 HTTP Message Signatures**, **ephemeral HPKE KEM-MACs**, **DRISL CIDs**, **2048-byte `LtHash` commits**, and **`@atproto/star` archives**.
- **Shared-session modality Operator (`apps/operator`):** Uses a shared Group-DID OAuth grant (reauthorizable by any active effective human admin, with `0`-step `aborted_actor_revoked` and `>=1`-step audited `operationAdminTakeover`) to orchestrate multi-space modality operations, 1-webhook-per-space `notify` renewals, and content-free `getChanges` cursors (`dm1` and `inv1` stateless PoP tokens).
- **Sovereign personal-PDS Direct Messages (`@flock/client/dm`):** 1:1 and up to 100-participant group DMs hosted strictly on participants' personal PDSes (`com.atproto.memberspace.policy`), with **zero DM rows in SQLite** on either Operator or Group Host (`no-legacy-memberspace` ESLint boundary).
- **CRDT-style Tasks (`new.flock.ext.tasks`), bots (`apps/echo-bot`, `apps/webhooks`), and three zero-lock-in independent readers (`@flock/reader`):** Standalone readers for OpenSocial groups/channels (`independent.ts`), DMs (`independent-dm.ts`), and Tasks (`independent-tasks.ts`) built strictly on `@flock/protocol` and `@atproto/{space,star,lex-data,lexicon}`.

## 2. What Worked Really Well

### 2.1 `opensocial.group` Eliminated Massive Workspace Governance Boilerplate in R13
Replacing our R1–R12 bespoke `com.atproto.memberspace` workspace governance with `opensocial.group` (`8df0cc82`) immediately resolved four major architectural pain points we had previously tracked as upstream requests (`.ai/upstream/{U3,U4,U7,U10}.md`):
1. **`O(1)` membership across 100 channels (`U7`):** Moving from per-space member lists to `group.opensocial.policy` (`grants: [{ role, read, write, scopes? }]`) referencing `role/*` and `membership/*` in `members/self` turned adding/removing a member across 100 channels from `~102` sequential XRPC calls + a 1-minute `reconcile-workspaces` cron job into **a single `putRecord(membership/<did>)` write (`<= 250 ms`)** and let us delete `reconcile-workspaces` completely.
2. **Zero shared personal-account password custody (`U4`):** Two-sided Group Host OAuth (`prompt=create` + personal-PDS sign-in + live `effectiveMemberPermissions` & `assignable` narrowing) eliminated dedicated workspace passwords while supporting both per-moderator/per-admin direct sessions (`GroupClient`) and Operator's shared application session.
3. **Member-readable roles & bilateral roster (`U3`):** `members/self` (`role/*`, `membership/*`, `acceptance/self`, and host-maintained `space/*`) let us delete 7 bespoke Flock governance lexicons (`workspace.profile`, `workspace.roster`, `admin`, `acceptance`, `channel.roster`, `permissions.workspaceAuthority`, `operator.listInboxWriters`).
4. **Standardized cross-PDS invitations & ATProto-native moderation (`U10`):** `at://<userDid>/space/group.opensocial.invites/self` plus `createReport` / `listModSubjects` / `getModSubjectHistory` / `resolveModSubject` and `<groupDid>`-authored `com.atproto.label.record` (`!takedown`, `!hide`) fit cleanly onto core Spaces without inventing chat-specific moderation primitives.

### 2.2 Core `#5187` (`6747610566`) Spaces Primitives Proved Solid
Inline `authorizeSpaceSync` (`{ credential, spaceRev }`, `notify`), `listWriters` (`#repoWrite` / `#repoRemoved`), batched `com.atproto.memberspace.{putMembers,removeMembers}` (for 100-participant DMs), every-page MAC-verified `listRepoOps`, and `@atproto/star` `getRepo` / `exportSpaceMeta` / `importSpaceMeta` / `importRepo` composed cleanly across both personal PDSes and `apps/group-host`.

## 3. Concrete Feedback & Recommendations for `opensocial.group` (R13 Findings)

Building a full production-grade reference Group Host (`apps/group-host`), browser/Node SDK (`@flock/client`), shared-session Operator, and two-host migration suite against `opensocial.group/proposal` @ `8df0cc82` surfaced six concrete specification gaps and edge cases we recommend addressing upstream:

### 3.1 Formalize `Idempotency-Key`, Queryable `join-status`, and Atomic `If-Join-Request-Present` Approval (`group.opensocial.requestJoin`)
- **What happens today:**
  1. `group.opensocial.requestJoin` mutates server state (redeeming/deleting single-use `invite` records or creating `join_request` entries), yet defines no `Idempotency-Key` header. If a mobile/browser client loses the HTTP response on an invite redemption, retrying `requestJoin` hits `400 InvalidInvite` (because the invite was already consumed) or risks ambiguity if the user was subsequently ejected.
  2. When `requestJoin` returns `{ status: "pending" }` (`joinPolicy === "approval"`), ordinary members hold no Group-DID `authModerate` grant to call `listJoinRequests`. Clients have no standard Personal-Auth query to distinguish *"still pending"*, *"approved (`admitted`)"*, *"denied"*, *"expired"*, or *"group migrated to a new Group Host where private `join_request` state did not migrate (`proposal.md:163`)."*
  3. Moderator approval writes `membership/<member>` via `com.atproto.space.putRecord`. Without an atomic precondition checking that an unexpired `join_request` still exists, a moderator approving a request milliseconds *after* the user called `cancelJoinRequest` silently admits a user who withdrew their request!
- **What we implemented & recommend standardizing:**
  1. **Optional `Idempotency-Key` (`1..128` `[A-Za-z0-9._:-]`) on `requestJoin`:** Bound to `(groupDid, callerDid, key)` + canonical request hash (`409 IdempotencyParameterMismatch` on mismatch; bounded per-requester unexpired quota `429 JoinOperationQuotaExceeded`), automatically upgrading stored `'pending'` state to `'admitted'` whenever `membership/<callerDid>` is created (even via direct `putRecord`/`applyWrites`).
  2. **Personal-auth `join-status` query (e.g., `group.opensocial.getJoinStatus`):** Authenticated with the caller's `requestJoin` RPC permission, **checking live durable `membership/<iss>` in `members/self` FIRST** (so a request approved right before a Group Host migration still returns `{ status: "admitted", membership }` on the target host!) before consulting private operation/queue state (`"pending" | "denied" | "cancelled" | "unknown"`), enabling clients to cleanly surface `"orphaned_by_migration"` when `currentEndpoint !== submittedEndpoint`.
  3. **Atomic `If-Join-Request-Present: true` header (or dedicated `approveJoinRequest` XRPC):** Verified inside the same `IMMEDIATE` transaction that writes `membership/<member>`, deletes `join_request`, and updates operation state (`409 JoinRequestNotFound` if cancelled, denied, or expired).

### 3.2 Add Generation / Incarnation Counters to `membership` & `acceptance` and Conditional `leaveGroup`
- **What happens today:**
  1. Bilateral roster display pairs `<groupDid>`-authored `group.opensocial.membership/<did>` with `<did>`-authored `group.opensocial.acceptance/self`. However, `acceptance.createdAt` (`acceptance.json:9`) is an unverified client-supplied string with no future clock bound. If a user writes `acceptance/self` with `createdAt: "2099-01-01T00:00:00Z"`, is ejected by an admin (`membership/<did>` deleted while `acceptance/self` remains on the user's personal PDS), and is later re-admitted (`membership/<did>` recreated), naive `acceptance.createdAt >= membership.createdAt` pairing immediately treats the stale pre-ejection `acceptance` as fresh consent!
  2. Worse, if Device A starts `leaveGroup` offline, crashes, and wakes up *after* the user rejoined on Device B (or after the group migrated to another Group Host), replaying an unconditional `leaveGroup` + `com.atproto.space.deleteRecord(acceptance/self)` (which lacks `swapRecord` CAS in `deleteRecord.json:12`!) silently destroys the newer membership and acceptance!
  3. Minor schema mismatch: `proposal.md:40` states every `membership` must grant at least one role, but `membership.json:13` omits `"minLength": 1` on `roles`.
- **What we implemented & recommend standardizing:**
  - Add `"minLength": 1` to `membership.roles` in `membership.json`.
  - Add first-class `incarnation` (UUID / opaque token minted on absent → present `membership/<did>`, preserved across in-place role edits, and carried verbatim in `space.getRepo` / `space.importRepo` STAR archives; we also fall back deterministically to `"legacy-cid:" + cid` for unannotated third-party imports) and `generation` / `afterWriterRev` fields to `group.opensocial.membership`, echoed as `incarnation` in `group.opensocial.acceptance`.
  - Support `If-Match-Membership-Incarnation` on `group.opensocial.leaveGroup` (`409 MembershipIncarnationMismatch` when stale) and execute `leaveGroup` **before** deleting own-PDS `acceptance/self` (so `400 LastAdmin` and `409 MembershipIncarnationMismatch` never corrupt `acceptance/self`), and add `swapRecord` CAS to `com.atproto.space.deleteRecord`.

### 3.3 Standardize `group.opensocial.policy` Host Capability Discovery, Multi-Key `rotationKeys` Provenance & Coordinated Migration
- **Three sharp edges surfaced in two-GroupHost migration (`proposal.md:9,46,161-171`):**
  1. **No pre-cutover `group.opensocial.policy` capability advertisement:** `proposal.md:9` forbids migrating an OpenSocial group onto an ordinary ATProto PDS that does not enforce `group.opensocial.policy`, yet `com.atproto.server.describeServer` looks identical on both! Without a verifiable pre-cutover capability signal, a source Group Host signing a PLC cutover op can accidentally brick a group onto a plain PDS.
  2. **Ambiguous multi-key `did:plc` `rotationKeys` during `createAccount`:** On 1-key groups (`rotationKeys = [K_0]`), Standard `createAccount({ did, handle, recoveryKey? })` works with zero extensions (if `recoveryKey === K_0`, `K_0` is sovereign; else `K_0` is the retiring source host's key). On **multi-key (`>= 2` `rotationKeys`)** groups holding both a source-host rotation key and external sovereign custody keys, PLC's untagged `rotationKeys` array cannot distinguish which key belongs to the retiring source host—risking either retaining the old host's rotation key (`SourceRotationKeyRetained`) or dropping a sovereign key (`SovereignRotationKeyDropped`)!
  3. **Live write races during uncoordinated migration:** Standard `getRepo` → `importRepo` without a source freeze allows concurrent channel creates, invites, or membership edits to land on the source host after export and be lost at PLC cutover.
- **Recommendations:**
  1. Standardize DID-bound host capability discovery: publish `{ id: "#opensocial_group", type: "OpenSocialGroupHost", serviceEndpoint }` on the Group Host's `did:web` document (and/or a signed `/group-admin/migration-info` capability JWT advertising `supportedSpacePolicies: ["group.opensocial.policy"]`).
  2. Standardize host-rotation-key provenance: either an authenticated `<groupDid>#atproto`-signed endpoint (`/group-admin/public-group-keys` returning `{ groupDid, localRotationKey, proofJwt }`) and/or a sovereign-key-signed JWS header (`X-Group-Migration-Key-Provenance`) on `createAccount`, plus a standard controller-session bootstrap (`POST /group-admin/controller-session` signed by an external PLC `rotationKeys` entry) so zero-human / externally governed groups (`proposal.md:46,169`) have uninterrupted post-cutover and ongoing custody.
  3. Standardize an opt-in **Coordinated Atomic Migration** profile (`prepare-migration` source lease + RFC 8785 JCS manifest → target `migration-manifest` pull & `100 MiB` import/blob caps → source-pulled `migration-attestation` before `signPlcOperation` → `submitPlcOperation` → `activateAccount` → idempotent `finalize-migrated-source`).

### 3.4 Clarify `createReport` Validation on Member-Authored Personal-PDS Records (`space_writer`), `<groupDid>` Account Subjects & Personal Auth
- **What happens today:** `createReport.json` accepts `subject` (`format: "uri"`) + optional `cid`. Because member and bot space records (messages, reactions, comments) reside on **personal PDSes** rather than on the Group Host (`proposal.md:19,57,143`), a Group Host implementer reading `createReport` naively might either (a) check local `space_record` storage (breaking reports on all member-authored messages!) or (b) check `membership` alone (allowing bogus reports attributing records to passive readers who have never written to that space, or failing after a writer's role changed). Conversely, `createReport.json:18` allows reporting an account DID, and `proposal.md:44,46` gives `<groupDid>` implicit self-membership with **no** `membership/<groupDid>` record.
- **Recommendations:**
  1. Specify normatively that for space-record subjects (`at://<groupDid>/space/<type>/<skey>/<repoDid>/<collection>/<rkey>`), Group Host verifies the caller holds live `read` access to that space (returning uniform `400 InvalidSubject` on missing/private spaces to avoid leaking private-space existence!), validates `repoDid === groupDid` against local `space_record` (matching `cid` when supplied), and validates `repoDid !== groupDid` against **`space_writer`** in that target space (`parseCid(cid)` when supplied).
  2. Specify that account-DID subjects (`cid` forbidden) accept both `membership/<subject>` entries and `subject === groupDid` (placed in `members/self`).
  3. Specify that all four personal service-auth methods (`requestJoin`, `cancelJoinRequest`, `leaveGroup`, `createReport`) reject `iss === groupDid` (`400 CannotTargetGroupSelf`).

### 3.5 Specify `com.atproto.label.record` Key/Value/Placement Invariants & Align Upstream Validation Fixtures
- **`com.atproto.label.record` invariants:** State normatively at write and `space.importRepo` time that `<groupDid>`-authored `com.atproto.label.record` requires: (a) `isValidTid(rkey)` (`label/record.json:8`), (b) non-empty `val.length >= 1` (`EmptyLabelValue` — `label/defs.json` allows `string`, whereas `getModSubjectHistory`'s `labelEvent.val` in `group/opensocial/defs.json:129` requires `minLength: 1`!), (c) account labels (`isDid(uri)`, `cid === undefined`) placed strictly in `at://<groupDid>/space/group.opensocial.members/self`, and (d) space-record labels placed strictly in the target record's own space (`400 CrossSpaceLabel` otherwise). Also state explicitly that `!takedown` is a syncer/client projection rule (latest `cts`, keeping raw records in writer repos so `LtHash` verification remains intact).
- **Upstream `opensocial.group/proposal` (`8df0cc82`) artifact alignments:**
  1. `validate-lexicons.mjs:251` still references the removed `#atproto_space_host` fragment instead of `${group}#atproto_pds`.
  2. `examples/records.json:88-94` uses `at://.../space/group.opensocial.meta/self` as its `group.opensocial.space` example, contradicting `proposal.md:36` (*"The `members` space indexes the group's modality spaces with a `space` record per space"*—core `meta/self` and `members/self` should be excluded).
  3. Enforce `http:` / `https:` URL schemes on `group.opensocial.profile.url` (`profile.json:38-41`, since Lexicon `format: "uri"` admits `javascript:` / `data:`), and document that `policy.grants[].scopes` expansion (`proposal.md:54-55`) must reject `manage=create`, non-`space:` scopes, and cross-space `(spaceType, authority, skey)` targets (`InvalidSpacePolicyScope`).
  4. **`group.opensocial.authParticipate` `"skey": "self"` vs `com.atproto.space.listSpaces`:** On `@atproto/pds`, `com.atproto.space.listSpaces({ spaceType: "group.opensocial.members" })` asserts `{ spaceType: "group.opensocial.members", authority: "*", skey: "*" }, { action: "read_self" }`. Because `authParticipate.json` sets `"skey": "self"` on its `group.opensocial.members` permission, `@atproto/oauth-scopes` rejects `listSpaces` with `Missing required scope "space:group.opensocial.members?authority=*&action=read_self"` unless `authParticipate` also includes an `skey`-unconstrained `{ "type": "permission", "resource": "space", "spaceType": "group.opensocial.members", "authority": "*", "action": ["read_self"] }` entry (or `listSpaces` adds an optional `skey` filter).

### 3.6 Publish Official `_lexicon.opensocial.group` DNS TXT + `com.atproto.lexicon.schema` Records
- **Production deployment blocker discovered against real `@atproto/pds` (`oauth-provider.ts:789`, `lexicon-manager.ts:179`):** On any pinned ATProto personal PDS, `OAuthProvider.authorize()` calls `lexiconManager.getSpacesFromScope()`, which resolves **both** `include:` permission sets **and every non-wildcard `space:<spaceType>` NSID** (`group.opensocial.meta`, `group.opensocial.members`, `group.opensocial.invites`) via `_lexicon.opensocial.group` DNS TXT → XRPC `com.atproto.lexicon.schema`! Expanding `include:group.opensocial.authParticipate` client-side into explicit `space:` scopes does **not** bypass `getSpacesFromScope()`'s space-NSID DNS resolution.
- **Recommendation:** Publish official `_lexicon.opensocial.group` DNS TXT + `com.atproto.lexicon.schema` records for all `27` `group.opensocial.*` lexicons so third-party clients can authenticate users on public ATProto PDSes (in Flock, `pnpm verify:lexicons` enforces this as a fail-closed launch gate).

## 4. Core ATProto Permissioned Spaces Recommendations (`6747610566`)

While `opensocial.group` resolved group roster visibility (`U3`), multi-admin Group-DID delegation (`U4`), `O(1)` 100-channel membership (`U7`), and cross-app group invitations (`U10`), the following core ATProto Spaces improvements remain high-leverage across both sovereign DMs and OpenSocial groups (standalone drafts in [`.ai/upstream/`](.ai/upstream)):

1. **Client-Direct Change Subscription (`subscribeSpace` — `U2`):** `authorizeSpaceSync(notify)` requires a public HTTPS webhook endpoint, forcing browser/mobile apps to run a server relay (`getDmNotifyTarget` `dm1` and `getSpaceNotifyTarget` `inv1`). An HTTP SSE / WebSocket `subscribeSpace` stream authenticated by `Atproto-Space-Credential` would eliminate relay metadata exposure completely.
2. **Write-Target Existence Signal on Cross-Host Writes (`U11`):** Cross-host `putRecord` returns `200 OK` even when the target space does not exist. While `apps/group-host` observes `notifyRepoUpdate` directly and tracks `invite_delivery` (`pending`/`delivered`/`failed`), personal-PDS writers (such as browser DMs) get no feedback and still require public `new.flock.dm.declaration` records. Returning an optional `spaceStatus` hint on `putRecord` or a write-scoped `getSpaceWriteStatus` query would remove public declaration records.
3. **Strict Zero-Skew `exp` Cutoff on Space Credentials (`U6`):** Keep `CLOCK_SKEW_SEC = 5` on `iat` and on `'delegation'` / `'clientAttestation'` tokens, and enforce `expirationSkew = 0` (`now >= payload.exp`) for `'credential'` tokens upstream so deployments can drop `strict-credential-expiry.patch`.
4. **Explicit Oplog Reset Signal in `listRepoOps` (`U12`):** Return `SinceUnavailable` (or emit `#repoReset`) when `since` predates `clearRecords` or `importRepo`, and ensure `clearRecords` on an empty repo still clears stale oplog entries.
5. **Host-Assigned Per-Record `rev`, `listRecords` Range Bounds (`U5`) & Personal-PDS Third-Party Validation (`U8`):** Expose commit `rev` per record and key/rev bounds on `listRecords` to defend against maximal `rkey` pinning, and support opt-in dynamic third-party Lexicon validation + machine-key slur-filter exemptions on personal PDSes.
6. **Decouple Server Webhook TTL from 10-Minute Read Credential TTL & Unify Loopback `devMode` Origins:** Allow longer `notifyTtl` / batch webhook renewal for backend syncers managing idle spaces, and allow `127.0.0.1` / `[::1]` in PDS `devMode` webhook `safeFetchWrap` alongside RFC 8252 loopback OAuth.
