# Operations

## Runtime configuration

Use the Node version in `.nvmrc` and install the locked dependency set with `corepack pnpm install --frozen-lockfile`. The app is two processes, each on its own origin: the web app (`corepack pnpm build && corepack pnpm start`), which needs `APP_URL`, `OPERATOR_URL`, `OPERATOR_SERVICE_REF` and `PLC_URL` and holds no database and no secret; and the operator (`corepack pnpm operator`), which needs those and `DATABASE_PATH`, `AUTH_ENCRYPTION_KEY` and, outside loopback development, `AUTHORITY_CLIENT_PRIVATE_JWKS` (see `.env.example`). The operator serves its XRPC methods, its inbound PDS webhook endpoints (`com.atproto.space.confirmRegistration` and `com.atproto.space.notifySpaceUpdate`), the authority flow and its `did:web` document (`/.well-known/did.json`, naming `OPERATOR_URL`) at `OPERATOR_URL`, and answers browsers of any origin on its methods (CORS with `*` and no credentials: a service token authorizes each call), while its authority flow answers none. Behind a proxy that terminates TLS, `PORT` is where the operator listens. In development both read the repository root's `.env` (copy `.env.example`): the web app's Next config takes from it only the variables the web app reads, and the operator's scripts (and `backup:db`) run Node with `--env-file-if-exists`; a variable the environment sets wins, so a deployment needs no file. The web app sets each page's Content-Security-Policy when it answers, with a nonce of that request's and `connect-src` from the `APP_URL` it runs with (`apps/web/src/proxy.ts`), so the build does not fix it. Public deployments require HTTPS for both URLs: in particular, upstream PDS `authorizeSpaceSync` and `SpaceNotifications` deliver `confirmRegistration` and `notifySpaceUpdate` through `ctx.safeClient(endpoint)`, whose SSRF protection blocks private, loopback, link-local, and reserved addresses unless the PDS runs with `devMode: true` and `disableSsrfProtection: true` (`L7`), so production `OPERATOR_URL` must be a publicly routable HTTPS origin. Production deployments using OAuth space-permission consent screens must also republish the updated `new.flock.*` space lexicons (where `"name"` moved to `"title"` across all 7 space schemas) along with `new.flock.operator.getDmNotifyTarget` and `new.flock.permissions.{member,workspaceAuthority}` (`L8`). The workspace authority account must approve the workspace-authority grant (below) before it can create spaces or authority records.

## Workspace authority grant

The operator administers every workspace with a grant its authority account approved, held per authority DID in the `authority_grant` table and encrypted like every other OAuth session. It is separate from the account's sign-in: signing in never writes it, signing out never revokes it, and it serves every admin of the workspace. The first workspace creation under an account asks for it; the flow is a two-minute single-use ticket, a top-level navigation to `/authority/start`, the PDS consent screen, and `/authority/callback`, which stores the grant only if the account that approved is the intended authority, from the browser that started the flow, within 15 minutes. Approving as any other account revokes that session and stores nothing.

A workspace belongs to its authority account, whose DID is in every URI of the workspace: the person creating it (who then needs only the grant, for any number of workspaces), or a dedicated workspace account they name. For a dedicated account, the person creating the workspace starts the flow from their own browser, and whoever can sign in as the account approves it there; that approval also leaves the person a creation authorization for that one workspace name, usable once within 15 minutes (`creation_authorization`). The person becomes the workspace's first admin and member; the dedicated account is neither, never signs in to the web app, and the workspace runs on its grant whoever the admins are. A creation makes a new workspace only, the account's own included: a name that already exists under the account, or that someone else's unfinished creation there claims, is refused (`WorkspaceExists`), and its admins (or its creator) add the person instead. An existing workspace cannot move to another account. Anyone may start the account's reauthorization (the app offers it to the workspace's admins when the grant lapses); it succeeds only for someone who can sign in as the account.

Outside loopback development the authority client is a confidential `private_key_jwt` client (metadata at `/authority/client-metadata.json`, public keys at `/authority/jwks.json`), which the PDS gives a two-year session. Its refresh token lapses after about three months without use, so the grant must be used at least that often; the scheduled reconcile job does. On loopback the client is public and its session lasts two weeks, as the PDS forces loopback clients public.

- **Keys.** `AUTHORITY_CLIENT_PRIVATE_JWKS` holds the private ES256 keys as a JWK set `{"keys":[...]}`, newest first; all are published at the JWKS route. Keep it in the deployment secret store, never in the database. A grant stays bound to the key it was approved with: its refreshes are always signed with that key, and only a new approval moves it to another. So rotation is: generate a key (`corepack pnpm authority generate-key <kid>` prints one private JWK; add it to the set), publish it second in the set and wait at least ten minutes (the JWKS answer is cached for five), then move it first so new approvals use it. Remove an old key only once every authority approved with it has approved again, or its grant was revoked. A grant whose key is gone answers "approve again" and keeps its row; putting the key back restores it.
- **Revocation.** `corepack pnpm authority revoke <did>` deletes the authority's grant and signs it out at its PDS. If the PDS cannot be reached the grant is still deleted, and the command says so and exits 1. Admin operations for that authority's workspaces then ask the account to approve again: an admin opens the permission screen, someone signs in there as the account, and the admin retries the pending operation. Replacing a grant (a new approval) signs the old one out the same way; a sign-out that fails there is recorded as an `authorityGrantRevocationFailed` audit event and the new grant stays.
- **Expiry, refusal, or temporary account suspension.** A grant the PDS no longer honors (expired, revoked, or short of a scope a release added; note that account-authenticated space/memberspace endpoints enforce `ACCESS_FULL` and reject app passwords with `InvalidToken: Bad token scope`, while `com.atproto.server.getServiceAuth` stays usable by app passwords), or one that cannot be decrypted with the current `AUTH_ENCRYPTION_KEY`, answers the same way, and the reconcile job reports `ALERT workspace authority grant is missing` or a failed reconciliation. A new approval replaces an unreadable grant, and `authority revoke` deletes one. By contrast, when a workspace authority account is temporarily suspended at its PDS (`401 AccountTakedown` or `AccountDeactivated` on management calls, or `400 RepoTakendown` / `RepoDeactivated` on `authorizeSpaceSync` or `listWriters`), the operator treats it as temporary account suspension: it stops retrying the current mutation and backs off notice renewal without deleting or revoking the encrypted `authority_grant` row, so the workspace recovers automatically once the account is restored.
- **Upgrading from a release before the grant existed.** Authority sessions held as sign-ins are not carried over: each workspace authority approves the grant once (the app asks when an admin operation or a new workspace needs it), and the reconcile job alerts for that authority's workspaces until it does.

The SQLite database stores the workspace authorities' encrypted grants and authority-flow state, the cross-process OAuth refresh lock, the operation journal, audit events, workspace/channel/inbox/extension notice registrations (`notification_registration` + `notification_registration_failure`) and content-free change notices (`space_notification`). It holds no member session, no member token, no member record, and **zero DM rows across every SQLite table**: people sign in in their browsers, which keep their sessions and what they read. A database from an earlier release drops its member session and cache tables when the app starts, and resets legacy `notification_registration` rows with empty `token = ''` to `expires_at = 0, renew_at = 0` so inline `authorizeSpaceSync` webhook tokens are provisioned immediately on startup. All web workers and scheduled reconciliation processes that use the same authority grants must share this local SQLite database file and encryption key. This SQLite deployment supports multiple processes on one host; multi-host replicas with separate local databases are unsupported. Keep the AES key outside the database and back it up in a separate secret store. Losing the key makes the stored authority grants unreadable (each authority approves again); it does not change PDS membership or records.

The app resolves PDS endpoints from account DID documents. It requires HTTPS for remote endpoints, rejects private, loopback, link-local, and reserved address results, and pins the validated address set in the outbound dispatcher for each 30-second DNS cache window. Production DID/PLC resolution, OAuth, space-credential, and operator-service requests use this checked fetch path. Only the isolated loopback PDS fixture in `NODE_ENV=test` uses the platform fetcher for its loopback PLC directory. Keep the deployment network policy denying outbound connections to private, loopback, link-local, and cloud metadata ranges as defense in depth, and limit the app's outbound path to the public AT Protocol services required by the workspace.

## Membership reconciliation and alerts

Run `corepack pnpm reconcile` from the app checkout, with the operator's environment, as a scheduled job every minute. Webhook registrations are made inline through `com.atproto.space.authorizeSpaceSync` (`notify: { endpoint, token }`) and share the issued space credential's lifetime (`600 s` default, `3600 s` ceiling). Each `(service_ref, space_uri)` row in `notification_registration` persists one stable random `token` (reused across all renewals so the PDS runs synchronous `confirmRegistration` only once on initial registration), `renew_at = exp * 1000 - min(3 min, floor(0.3 * ttlMs))`, and `last_space_rev` (emitting a wake row whenever `authorizeSpaceSync.spaceRev` advances across downtime or gaps). Because registrations expire with the 10-minute default credential, the running operator process (`corepack pnpm operator`) executes a **60-second SQL-first renewal loop** (`SELECT ... WHERE token = '' OR renew_at <= ?` joined with `notification_registration_failure`, retrying transient errors with `15 s -> 2 min` backoff under an in-process mutex and heartbeated renewable DB lease, making zero grant restores or PDS requests when nothing is due) alongside a **30-minute workspace discovery backfill sweep** (and immediate async renewal whenever `notifySpaceUpdate` delivers `#registrationExpired`). Registration sweeps skip while mutations are paused and warn with `WARN notice registration` about each space whose registration failed or ran out, which the admin screen also lists: such a space gets no push ticks, so clients fall back to periodic `listWriters` polling until it is restored. Warnings do not fail the run. `pnpm reconcile` also drops change notices older than a week and stale notice registrations that ran out a month ago, even while mutations are paused. It finds workspaces from the durable operator journal, reports operations stalled for five minutes before attempting recovery, restores each authority grant from the encrypted store, resumes incomplete workspace creations with that grant, checks current authority/admin records, resumes other saved operations, and reconciles stable workspace/inbox/channel/extension membership (via batched `putMembers`/`removeMembers`). When `FLOCK_ADMIN_MUTATIONS_PAUSED=true`, stalled-operation alerts and read-only authority/admin checks still run, while all mutations are skipped. Missing or revoked authority grants and failed workspace checks produce stderr output and exit code 1. Forward stderr to the operator's alert channel. The admin screen also shows stalled operations and reconciles every five minutes while open after an authorized admin operation.

The authority grant's OAuth client uses a per-DID SQLite lease to prevent simultaneous processes from consuming the same one-use refresh token. A stale lease left by a crashed process expires. Authority-flow state rows older than 30 minutes are pruned when state is read or written; the flow's browser cookie expires after 15 minutes. Grant writes and deletes retry SQLite busy/locked errors for three total attempts. If refreshed-token persistence still fails after those attempts, the OAuth library revokes and removes that grant, and admin operations ask the authority to approve again.

Every outbound request to a host someone else named (a PDS, an identity host, an authorization server) ends a minute after it began, counted from connecting to the last byte of the answer, so a host that stalls cannot hold a request open. The operator answers a request that ran out of time as a temporary upstream failure (503). Inside a journaled operation it leaves the operation pending without the immediate retries below, because repeating a stalled request would keep the workspace lock held. One run of an operation starts no step once it has held the workspace lock for three minutes: the operation stays pending with the steps it completed and a time-limit error, and continues when it is sent again. A client should allow about five minutes for an `execute` answer (the wait for the lock plus one run); one that gives up earlier loses nothing, since the operator carries on and the same operation sent again returns its state.

The operation journal is retry metadata. Each run retries recognized transient PDS/network failures for up to four total attempts with 100/200/400 ms backoff; permanent authorization and validation failures become pending/failed without retry. One exception: a workspace setup that fails because the account has not yet approved the required OAuth permission, before any step completed, is deleted from the journal (with an `operationDiscarded` audit event) and answered with a typed `authorization_required` response, so it never raises a stalled-operation alert. This also applies when recovery resumes such an empty row in the background; the user's retry simply creates a fresh one. A discarded creation under a dedicated account gives the person's creation authorization back, for that operation ID only and for 15 more minutes. A failure after some steps stays pending. Before an active admin starts a new mutation, the operator resumes earlier pending operations for that workspace so an old retry cannot override a newer decision. A member-scoped leave request does not trigger admin recovery; it waits with a busy response while an admin operation is pending. A leave, self-removal or self-demotion that stopped part-way can be sent again by the account that started it, even though it no longer holds the role it started with; the next admin mutation also resumes it. An unfinished workspace creation keeps its name claimed under its account until it completes, so fix what stops it (the reconcile job resumes it every minute) rather than creating the workspace again. If an operation remains pending, preserve the database, inspect its recorded step names and last error, verify the corresponding PDS member lists and authority records, then retry with the same operation ID from the admin screen. Do not edit a journal row to claim completion.

## Apps

An app is an account that publishes `new.flock.app.declaration` in its own repo and runs the client with its own OAuth session; no code of an app runs in the operator. An admin installs it with `installApp`, changes its channels with `updateAppAccess` and removes it with `uninstallApp`. Its install record (`new.flock.app.install`, in the workspace space) is the grant: the app reads the workspace space and each channel granted, writes where the grant says, and reads its own per-install inbox (`new.flock.app.inbox`), where every roster member writes slash commands (`new.flock.app.command`) and button clicks (`new.flock.app.action`). No other member or admin is granted read access to an app's inbox. Because a space's authority account always reads its own spaces at the host, in a self-owned workspace (where a person's account is the authority rather than a dedicated workspace account) that person's account could read app inboxes directly at the host; the web app requests no read scope on `new.flock.app.inbox`, and the operator uses its grant on an app inbox only to register change notices and never reads its records. A workspace holds at most 20 active apps, apart from its 200 people, so a member list holds at most 220 entries. An account is a person or an app in a workspace, never both. Archiving a channel ends every app's grant of it. Installing or changing an app ensures its inbox space first, writes the install record, and syncs the member lists; reconcile creates missing inboxes of pre-R10 active installs and moves every list toward the records, so an operation that stops is finished by its retry or by the next reconcile, never undone.

The install collection and `new.flock.app.inbox` joined the authority grant's scope with apps and interactions. A grant approved before then answers an install or access change at its first step with "the workspace authority must approve its permission again", leaves no journal row, and the admin retries the same operation after the account approves again; meanwhile the reconcile job completes for the workspace's other spaces and logs `WARN workspace=... workspace account must approve its permission again for app commands to work`.

An app whose grant is read only is never listed as a writer by the authority, so nothing it writes there reaches a reader; the same holds for every app in the workspace space. Changing an app's grant of a channel from write to read takes it out of the channel's writers too, and with it the messages it wrote there. After `uninstallApp` the app is in no member list, `getChanges` denies it at once (an operator process other than the one that removed it may answer from its cached member list for up to 60 seconds, as for a removed person), and the authority refuses it a new space credential. A credential it already holds still reads until it expires: the pinned PDS issues them for ten minutes (`protocol-tests/apps.test.ts` asserts both), so an uninstalled app can read for up to ten more minutes, as a removed person can. Removing an app also takes its earlier messages out of view, since it is no longer a writer of those channels.

### Running an app: the echo bot

`apps/echo-bot` is the first app and the pattern for others: a Node process that depends on `@flock/client` alone. Sign its account in once with `corepack pnpm echo-bot sign-in <handle>` (it prints the page to approve), set `ECHO_BOT_DID` to the DID it prints, list the workspaces it was installed in in `ECHO_BOT_WORKSPACES`, and run `corepack pnpm echo-bot run`. It serves its OAuth client metadata and public keys at `ECHO_BOT_URL`, which the account's PDS reads at sign-in and at every refresh, so the process must stay reachable there. Over https it is a confidential client and needs `ECHO_BOT_PRIVATE_JWKS`; on a loopback http URL it is a public client, whose session the provider ends after two weeks. `ECHO_BOT_STATE_FILE` holds the session's DPoP keys and tokens: it is created readable by its owner only, and is to be kept out of backups that others read and out of the repository. A refused refresh stops the bot with "sign the bot in again". An app is told its workspaces because it cannot find them itself: it is never a writer of a workspace space. Every host the bot reaches, its own account's PDS and authorization server included, goes through `@flock/net`: https to a public address only, so off loopback its account must live on a publicly reachable PDS. Its log escapes control characters in a failure's message, since some of that text (a sign-in callback's query, a host's error) comes from others.

## Pause and resume

Set `FLOCK_ADMIN_MUTATIONS_PAUSED=true` and restart/redeploy the app and operator process to reject administrative mutation requests, including workspace bootstrap and recovery. Reads, message sync, and existing PDS state remain available. Remove the variable and restart to resume. A pending operation can then be retried or picked up by the next reconciliation run.

## Database backup and recovery

Write backups to encrypted storage outside the live database directory. The script uses SQLite's online backup API, so it can run while the app is open. It creates a new destination file exclusively with owner-only permissions on POSIX systems and refuses to overwrite an existing file:

```sh
corepack pnpm backup:db /secure/backups/slack-2026-09-24.db
```

Back up the AES key separately with access controls at least as strict as the database backup. Retain enough versions to recover from accidental deletion or database corruption. Verify backups periodically by restoring one to an isolated path and starting the app against it; never test restoration over the live database.

For recovery, pause admin mutations, stop the operator, restore the selected database backup and its matching AES key, start the operator, verify workspace discovery and operation status, then run `corepack pnpm reconcile`. Resume admin mutations only after PDS member lists and authority records agree. PDS records and memberships are not rolled back by restoring this SQLite database.

## Direct messages: what an operator can and cannot see

DMs have no server-side member route, SQLite table, DM row, cache, or session of their own, and the server holds no member session at all (`ARCHITECTURE.md`, "Direct-message runtime boundary"). Optional low-latency DM push wakeups use two content-free operator endpoints (`new.flock.operator.getDmNotifyTarget` and `new.flock.operator.getChanges`):

- **Zero DM rows in SQLite.** Unlike workspace/channel notifications (which write to `space_notification` and `notification_registration`), DM notifications store **zero rows** in any SQLite table (`space_notification`, `notification_registration`, `notification_registration_failure`, `authority_grant`, `member_list`, `oauth_session`). Instead, `DmClient.watch` calls `new.flock.operator.getDmNotifyTarget` with a service JWT (`lxm=new.flock.operator.getDmNotifyTarget`), a valid unexpired `SpaceCredential` for that DM space, and a fresh RFC 9421 key-possession proof (`verifyCredentialSig` over `cnf.kid` with short-lived replay protection; the operator never holds the `cnf.kid` private key and discards the proof immediately). The operator derives a deterministic stateless per-`(space, callerDid)` `dm1` HMAC token from `AUTH_ENCRYPTION_KEY` via HKDF-SHA256 (`"flock-dm-notify-v1"`), so credential renewals reuse the same `(endpoint, token)` without re-triggering `confirmRegistration` or duplicating PDS registrations.
- **Ephemeral in-memory wakes & closed-tab cleanup.** Inbound `confirmRegistration` and `notifySpaceUpdate` (`#repoWrite`, `#repoRemoved`, `#spaceDeleted`) verify `dm1` tokens in constant time (with zero DID resolutions per webhook and zero SQLite writes) and advance a bounded process-local in-memory wake ring (`apps/operator/src/operator/dm-feed-wakes.ts`) merged into `new.flock.operator.getChanges` (which emits `reset` after an operator restart so `ChangeFollower` resyncs once). When a closed browser tab's DM credential lapses and the PDS sends `#registrationExpired` for a `dm1` token, the operator returns HTTP `400`, triggering PDS `abandonSyncerNotice` so the PDS drops the expired registration immediately rather than retrying for 72 hours.
- **Known residual exposure, stated not solved:** Although direct SQLite inspection reveals zero DM rows, an operator inspecting live process memory (`dm-feed-wakes.ts`) or HTTP access logs (`getDmNotifyTarget`, `notifySpaceUpdate`, `getChanges`) can still observe timing and social-graph metadata: which caller DIDs requested notify targets or polled `getChanges` for which conversation-half or inbox space URIs (a conversation key is a TID, not a secret), and when `notifySpaceUpdate` arrived from a participant's PDS. Because `authorizeSpaceSync` webhook delivery targets an HTTPS endpoint (`L7`), a browser-only client still relays change ticks through a server until a browser-direct subscription mechanism exists upstream.
- **Non-blocking fallback & pre-R12 session compatibility:** The change feed and webhook registration are never on the DM correctness path — `renotifyPending()` and `DmClient`'s periodic `listWriters` poll are. If `getDmNotifyTarget`, `confirmRegistration` (`RegistrationNotConfirmed`), SSRF protection, or missing scope (`ScopeMissingError` on a pre-R12 browser session granted before `getDmNotifyTarget` existed, which `apps/web/src/browser/session.ts` keeps signed in) prevents webhook setup, `DmClient.watch` immediately mints `authorizeSpaceSync` **without** `notify` so DM reads and writes never fail.
- An operator cannot, through the app or its API: read any DM message, reaction, or inbox request body; mint a DM `SpaceCredential` (nor sign with a caller's non-extractable `cnf.kid` key); enumerate a user's unfollowed conversations; or revoke, delete, or export anyone's DMs.
- No server route handler (`apps/web/src/app/**/route.ts`) may import `packages/client/src/dm/**`; this is enforced by an ESLint `no-restricted-imports` rule in `eslint.config.mjs`, not only by convention.

## Release checks

The PDS implementation and lexicons are pinned in [`protocol/atproto-spaces-pin.md`](./protocol/atproto-spaces-pin.md). Any pin change blocks release until the multi-PDS suites and app acceptance matrix pass again. Deployment, pilot enrollment, and an external alert destination are release tasks; this repository supplies the app, reconciliation command, local alert output, pause switch, and recovery instructions.

### Deployment and acceptance sequence

1. Build the reviewed revision with the locked Node and pnpm versions. Configure production secrets outside the checkout and enforce the documented network policy.
2. Deploy the app and the one-minute reconciliation job on the same host and shared database/key. Confirm the public app responds over HTTPS, OAuth callbacks complete, DID service resolution and PDS connectivity work, and the authority's read-only checks succeed.
3. Exercise the pause switch, pending-operation status and retry, alert delivery, encrypted backup, and isolated restore before inviting pilot members. Confirm a paused reconcile still reports stalled operations and performs no mutations.
4. Enroll only the named pilot DIDs. Record evidence for two-app workspace discovery, public message/reaction parity, private request and approval/denial, membership removal and credential expiry, missed-notification recovery, and restart/reconciliation recovery.
5. Observe the pilot for the agreed window. Track reconciliation completion within 60 seconds, stalled-operation alerting at five minutes, failed OAuth/PDS calls, and any membership mismatch. Pause admin mutations and follow the recovery procedure if PDS and authority state diverge.
6. Expand only after the workspace owner and pilot operator record acceptance of the PRD criteria, review the evidence, and confirm the deployed PDS revision still satisfies the pinned protocol checks.

Keep a restricted release record containing app commit/build identity, PDS revisions and strict-expiry evidence, deployment URL, backup/restore result, alert test, pilot window and cohort identifier, acceptance evidence, incidents, and owner/operator sign-off. Keep the member enrollment list access-controlled and separate. Do not include credentials or private message contents in the release record.

## Cached data retention

The server keeps no copy of any space's records. Each person's browser keeps what it read in its own store, one per account. Signing out deletes the account's store and its DM state; an account starting in a browser deletes the store another account left there (a crash before its sign-out); and at each start a space not opened for 30 days is dropped. The browser drops a space's copy when its credential for the space is refused or the space is reported deleted, and drops one non-authority writer's records when that writer's repo is permanently unreadable (while preserving cached authority records if the authority's own repo returns `RepoTakendown` or `RepoDeactivated` during temporary suspension). The reconcile job drops change notices older than a week and notice registrations that ran out a month ago; when `notifySpaceUpdate` delivers `#spaceDeleted` for an operator-managed space, the operator first confirms deletion by calling `authorizeSpaceSync` through the workspace's authority grant and purges that space's notices, cached member list, and registration rows only when the authority confirms `SpaceDeleted` (preserving state on transient or account-suspension responses).
